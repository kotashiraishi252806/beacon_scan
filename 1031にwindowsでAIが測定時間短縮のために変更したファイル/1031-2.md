## 変更A:2回目以降のスキャンで全BSSIDを接続試行の対象にする

### 原因(1030.md の事実2の説明)

セッション2回目以降のスキャンでは、スキャン結果を「1回目に選択したBSSID」でフィルタしていた。

```kotlin
// 変更前 ConnectionMeasurementActivity.kt:885
val targetAps = apList.filter { it.bssid in selectedBssids }
```

- `selectedBssids` は1回目のスキャン後にAP選択画面で選んだBSSIDの集合(`:302`)。
- 測定・保存されるのはこの `targetAps` のみ(`:889` → `:641` → `:675`)。
- そのため scan2〜6 に新しいBSSIDが現れることはなく、scan1 の検出数がlabel全体の重複排除BSSID数と一致していた(1030.md 事実2)。
- 測定時は scan ごとに数十メートル移動しているため、scan1 の地点で選んだBSSIDの多くが届かなくなり、scan2〜6 の検出数が10〜20件程度に減っていた。
- 1回のみのスキャン(1030.md 事実4)は新規セッションの scan1 なので、フィルタがかからず多く検出されていた。
- scan1 の保存件数も「スキャン検出数」ではなく「選択したAP数」(`:284`)である。

スキャン(`startScan()`)自体は毎回全チャネルを対象に行われており、フィルタはスキャン後のアプリ側処理である。

### 変更内容

```kotlin
// 変更後 ConnectionMeasurementActivity.kt:883-885
// セッション2回目以降：今回検出した全BSSIDで自動測定
if (sessionId != null && selectedBssids.isNotEmpty()) {
    val targetAps = apList.toList()
```

- セッション中かどうかの判定(`selectedBssids.isNotEmpty()`)は残した。1回目のAP選択画面は従来どおり表示される。
- `:890-900` の「選択済みBSSIDが検出されませんでした」ダイアログは表示されなくなった。検出0件の場合は `:813` で先に処理が終わるためである。コードは削除していない。

### 影響

- scan2 以降の接続試行件数が増える。1件あたり最大10秒(変更B後は打ち切り条件により短縮)、件と件の間に0.3秒の待ちがある。

## 変更B:接続試行の打ち切り条件の追加

### 追加した定数(`SupplicantMeasurer.kt:28-29`)

```kotlin
private const val FIRST_STATE_TIMEOUT_MS = 3_000L // 試行開始から最初の状態を待つ時間
private const val NEXT_STATE_TIMEOUT_MS = 3_338L  // 状態受信後に次の状態を待つ時間
```

### 仕組み

2つの打ち切り条件を1本の「状態無変化タイマー」で実装した。

- `idleHandler`(メインスレッドの Handler)と `idleTimeoutRunnable` を追加。
- 時間切れになると `idleExitOccurred = true` を立てて、待機中のコルーチン(`supplicantContinuation`)を再開し、試行を終える。
- タイマーは、Supplicant状態を受け取る BroadcastReceiver と同じメインスレッドで動くため、両者が同時に走ることはない。

### タイマーの開始・リセット・停止

| タイミング | 処理 | 箇所 |
|---|---|---|
| 開始 | `requestNetwork()` を呼ぶ直前に 3000ms でセット | `SupplicantMeasurer.kt:210` |
| リセット | 試行中に状態を受信するたびに、止めてから 3338ms でセットし直す。現行の早期終了判定(`when (state)`)より前に行う | `:98-99` |
| 停止 | 試行が終わったら必ず止める。終わり方(早期終了・新しい打ち切り・10秒上限・onAvailable)によらない | `:226` |

- 状態を受信してリセットするのは、試行中(continuation が有効な間)だけである。
- 試行全体の上限10秒(`withTimeoutOrNull(DIALOG_TIMEOUT_MS)`)は変更していない。
- 現行の早期終了条件(COMPLETED、DISCONNECTED、ASSOCIATED)は変更していない。

### final_state の判定順(`:235-250`)

1. `REQUEST_FAILED`(接続要求APIが例外で失敗。後述)
2. `NETWORK_AVAILABLE`
3. `PRE_TIMEOUT_ASSOCIATED`(ASSOCIATEDで次へ進む方式のとき)
4. `AUTH_COMPLETED` / `PRE_TIMEOUT_<状態>`(現行の早期終了)
5. `IDLE_NULL` / `IDLE_<最も進んだ状態>`(今回追加した打ち切り)
6. `TIMEOUT_<状態>` / `TIMEOUT_NULL`(10秒上限)

### 新しい接頭辞:`IDLE_`

| 打ち切り条件 | final_state |
|---|---|
| 試行開始から3000ms、状態が1つも来ない | `IDLE_NULL` |
| 状態受信後3338ms、次の状態が来ない | `IDLE_<それまでに到達した中で最も進んだ状態>` |

`IDLE_` を選んだ理由:既存の接頭辞(`TIMEOUT_`、`PRE_TIMEOUT_`、`AUTH_`、`NETWORK_`)と文字列が重ならないため、分析時に `startsWith("TIMEOUT_")` などの判定で混ざらない。

### 接頭辞の後ろの状態名

修正版の1031.mdの指定に従い、`TIMEOUT_` と同じく「それまでに到達した中で最も進んだ状態」を付ける。`TIMEOUT_` と同じ関数 `mostAdvancedState()` を使う。順位は DISCONNECTED < INACTIVE < SCANNING < AUTHENTICATING < ASSOCIATING < ASSOCIATED < FOUR_WAY_HANDSHAKE < GROUP_HANDSHAKE < COMPLETED。この順位表にない状態(INTERFACE_DISABLED など)は最下位として扱われる。

初版では「最後に受信した状態」を付けていたが、修正版の1031.md(2026/10/31)を受けて変更した。

## 変更B:接続要求APIのログ

### 記録対象

現行コードで接続要求を出しているAPIは `ConnectivityManager.requestNetwork` のみである。ネットワークの追加(`addNetwork`)や接続(`enableNetwork` など)は使っていない。`WifiNetworkSpecifier.Builder.build()` が失敗した場合は従来どおり `SKIPPED` になり、`requestNetwork` は呼ばれない。

### 記録する項目

| 項目 | 内容 |
|---|---|
| api | 呼んだAPI名(`"ConnectivityManager.requestNetwork"`) |
| elapsed_ms | 呼んだ時刻(試行開始からの経過ms) |
| result | `"OK"`、または例外時は `"<例外クラス名>: <メッセージ>"`(`requestNetwork` は戻り値なし) |

### 例外時の動作の変更

変更前は `requestNetwork` が例外を投げるとアプリが落ちていたと考えられる(例外を捕まえていなかった)。変更後は例外を記録し、その場で試行を終えて final_state を `REQUEST_FAILED` にする。

### 記録方法:送信JSONと端末内ログの両方

- 端末内ログ:`Log.d("BeaconScan", "requestNetwork <bssid> at <ms>ms -> <結果>")`
- 送信JSON:試行ごとに final_state と並べてサーバ側で集計できるため、JSONにも含めた。

### 追加したJSONキー(サーバ側DBの変更が必要)

各 access_points 要素に次のキーを追加した(`ConnectionMeasurementActivity.kt:958`)。

```json
"supplicant_api_calls": [
  { "api": "ConnectivityManager.requestNetwork", "elapsed_ms": 2, "result": "OK" }
]
```

| キー | 型 |
|---|---|
| supplicant_api_calls | 配列(SKIPPED・未測定のときは空配列 `[]`) |
| api | 文字列 |
| elapsed_ms | 整数(long) |
| result | 文字列 |

データ型は `ScanData.kt` に `SupplicantApiCall(api, elapsedMs, result)` を追加し、`AccessPoint` に `supplicantApiCalls`(既定値は空リスト)を追加した。

## 1031.md の質問3への回答:試行と試行の間に入る処理

- 毎回 `delay(300)`(300ms)が入る(`SupplicantMeasurer.kt:155`)。
- 画面更新のコールバック(`onApFinished` / `onProgress` / `onApStart`)が入る。
- `supplicant_elapsed_ms` は `measureForAp` に入った時点から測っているため、上記は含まれない。50件なら1スキャンあたり少なくとも15秒が、1031.md の短縮時間の計算に入っていない。
- `unregisterNetworkCallback` は前の試行の中で実行されるため、前の試行の elapsed に含まれる。
- スキャンとスキャンの間には、保存・送信、「次の測定場所」ボタンを押すまでの待ち、位置情報の取得(`getCurrentLocation`)が入る。

## 提案(未実施)

### 提案1:onUnavailable の記録を追加する

コメントには「onUnavailable で早期終了」と書かれているが、実際の NetworkCallback は `onAvailable` しか実装していない。`onUnavailable` を記録用に追加すれば、OSが接続要求を断った場合(TIMEOUT_NULL / IDLE_NULL の原因候補)を記録できる。なお `requestNetwork` にタイムアウト引数を渡していないため、`onUnavailable` が呼ばれる条件は端末・OSバージョンによる。

### 提案2:スキャン処理のログを追加する(1030.md 質問2)

`onScanResultsReady` と `startScan` に次のログを追加する。

- `startScan()` の戻り値と呼んだ時刻(`ConnectionMeasurementActivity.kt:777`)。現在は false のとき Toast を出すだけで記録されない。
- ブロードキャストの受信時刻、`EXTRA_RESULTS_UPDATED` の値、`:788` の条件で捨てたかどうか。現在は `EXTRA_RESULTS_UPDATED` を読んでいない。
- `rawResults.size`、`grouped.size`(フィルタ前)、`targetAps.size`。
- 各 ScanResult の経過時間(`SystemClock.elapsedRealtime()*1000 - ScanResult.timestamp`)。キャッシュされた古い結果の判定用。
- 結果に含まれる周波数の種類数。一部チャネルのみのスキャンの判定用。
- getScanResults 時点の `wifiManager.connectionInfo.supplicantState` と BSSID。

### 提案3:スキャン開始前に届いたブロードキャストの扱い

`isScanInProgress = true`(`:759`)は位置情報取得の前に立ち、`startScan()`(`:777`)は位置情報取得の後に呼ばれる。その間にOS由来の SCAN_RESULTS_AVAILABLE が届くと、アプリが要求したスキャンではない結果で処理が進む。提案2のログで実際に起きているかを確認する。

### 提案4:使われなくなったダイアログの扱い

変更A により `ConnectionMeasurementActivity.kt:890-900` の「選択済みBSSIDが検出されませんでした」ダイアログは表示されなくなった。削除するか残すかを決める。
