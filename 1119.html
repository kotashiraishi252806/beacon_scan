5.2 サプリカント状態取得機能

5.2.1 概要

これまで無線LAN環境の把握に資する指標として、RSSI が広く用いられてきた。RSSI とはモバイル端末が無線LANアクセスポイントから受信した電波強度を表す物理層の指標であり、これを可視化したヒートマップによって電波受信状況を把握することは可能である。しかしながら RSSI は、物理層より上位のレイヤにおける接続可否や通信状況を反映する指標ではないため、HTTP などの上位層プロトコルを用いる Web サイト閲覧や動画視聴の可否を把握する用途には適していない。

上位層通信の可否を把握するための指標としては、スループットが知られている。スループットを測定することにより、電波の到達範囲に加え、通信状況や品質に関する詳細な情報を得ることが可能となる。しかしながらその測定にはアクセスポイントとの認証成立が前提となり、認証前の段階において測定することはできない。本研究は周辺の無線LAN環境を網羅的に把握することを目的としているため、認証を要する指標のみに依拠した場合、認証情報を保有しないアクセスポイントとの通信可否を観測することが不可能となり、目的の達成に対する制約となる。

この制約に対し、先行研究 [1] においては、認証成立前にモバイル端末上で取得可能な指標として、サプリカント状態の遷移が提案されている。サプリカント状態とは、wpa_supplicant が管理する認証・接続の進行段階を示す状態機械の値であり、Android 端末においては SUPPLICANT_STATE_CHANGED_ACTION ブロードキャスト [2] を介して取得することができる。本指標は RSSI よりも上位のレイヤにおけるアクセスポイントとの双方向通信の進行度を反映しており、認証が成立する以前の段階においても、アクセスポイントとの通信可否を推定し得る点に特徴を有する。[確認済: SupplicantMeasurer.kt:17, 98-144, 298-306]

先行研究においては、サプリカント状態の遷移内容が無線LANセキュリティ規格に応じて変化することが報告されている。認証を要する WPA2 および WPA3 においても、認証前段階における状態遷移を観測することによってアクセスポイントとの通信可否が把握可能であるとされる。[未確認: 先行研究論文の該当節]

他方、先行研究における実測評価の対象は単一のアクセスポイントに限られていた[確認済: 先行研究サプリカント取得アプリ/MonitoringConnectingWifi.kt:58]。本研究が目的とする周辺無線LAN環境の網羅的な把握のためには、検出された個々のアクセスポイントについて通信可否を取得し得ることが必要である。したがって、単一アクセスポイントに限定された先行研究の測定範囲は、本研究の目的を達成するうえで不十分であると判断される。

以上を踏まえ、本機能では、WiFi スキャンによって検出された周辺のアクセスポイントに対し順次接続要求を発行し、各アクセスポイントに対するサプリカント状態の遷移を記録することを目的として実装を行った。[確認済: SupplicantMeasurer.kt:162-186]

5.2.2 機能詳細

本節での雛形からの訂正点:
  • プローブ要求と接続試行の関係: 雛形では「接続試行とは、端末が AP へプローブ要求を送信すること」と記述されていたが、IEEE 802.11 の用語上、これは誤りである。プローブ要求（Probe Request）はスキャン段階における AP 発見のための管理フレームであり、特定 AP への接続開始時に送信されるのは認証要求（Authentication Request）および結合要求（Association Request）である[要参考文献: IEEE 802.11-2020 §11.3]。本稿では「接続試行」を、端末が特定 AP に対して認証・結合手続きの開始を要求する動作と定義する。
  • ConnectivityManager の属性: 雛形では ConnectivityManager がハードウェアであるかのように記述されていたが、これは Android フレームワーク層のシステムサービスであり、ハードウェアではない[要参考文献: Android Developers ConnectivityManager ドキュメント]。本稿ではフレームワーク層のサービスとして記述する。
  • 徒歩速度の換算: 雛形では「秒速 1.5 m（時速 10 km）」と記述されていたが、1.5 m/s × 3.6 = 5.4 km/h であるため、時速 10 km は誤りである。本稿では「1.5 m/s（約 5.4 km/h）」に統一し、10 秒間に 15 m 離れるという試算を採用する[要参考文献: 徒歩平均速度の出典]。
  • onUnavailable の扱い: 雛形では「onUnavailable が通知される」と記述されていたが、現行実装においては NetworkCallback の onAvailable() のみが実装されており、onUnavailable() は実装されていない[確認済: SupplicantMeasurer.kt:216-224]。測定は、onAvailable の発火、サプリカント状態遷移の終端、無変化タイマー、全体タイムアウトのいずれかによって終了する。本稿では現行の挙動に即して記述する。
  • 雛形中の [参考文献 N] は暫定で [要参考文献: 概要] の形式で残している。番号確定後に差し替えるものとする。

全体の流れ

現時点における本機能は、測定者が静止した状態で 1 地点の測定を完結させることを前提として開発している[推測: 徒歩移動中の連続測定は主たる想定ではない]。測定手順は以下の 3 段階から構成される。

  1. スキャン（周辺アクセスポイントの検出）。
  2. 接続試行（検出された各アクセスポイントに対する認証・結合要求と状態観測）。
  3. データ送信（測定結果のサーバへの送信）。

スキャンおよび接続試行は、1 地点の測定において 1 セットとして実行される。測定者は、このセットを地点ごとに繰り返し、n 地点の測定を終えた時点において、最後にデータ送信を行う[推測: 実装上はスキャン完了直後の都度送信も可能であるが、本節では「n 地点終了後に一括して送信する」利用手順を前提とする]。

本節においては、上記 3 段階を処理単位に細分化した以下の 5 ステップについて、利用する Android API と、記録される情報とを対応づけて述べる。

  1. ステップ 1 ビーコンスキャン: 端末が自身の電波受信範囲内のアクセスポイントを検出する。
  2. ステップ 2 測定対象 BSSID リストの作成: 検出結果を BSSID 単位の一覧に整形したうえで、測定対象を確定する。
  3. ステップ 3 接続試行: 各 BSSID に対して順に接続試行を行い、サプリカント状態遷移を記録する。
  4. ステップ 4 ラベル付与: 各試行結果に対して最終状態ラベルを付与する。
  5. ステップ 5 データ送信: 全測定結果を JSON に整形し、HTTP を介してサーバへ送信する。

ステップ 1: ビーコンスキャン

本ステップは、端末が周辺アクセスポイントのビーコンまたはプローブ応答を受信し、これを検出する処理である。この手続きはビーコンスキャン機能と同一であるため、具体的な処理手順については 5.1.3 を参照されたい。本機能においては、スキャン完了時に WifiManager.scanResults から得られる ScanResult の一覧が次ステップの入力となる。[確認済: ConnectionMeasurementActivity.kt:816-848, 850-889]

ステップ 2: 測定対象 BSSID リストの作成

ステップ 1 において得られた ScanResult の一覧は、BSSID 単位のオブジェクト一覧へと整形される。この整形処理においては、同一 BSSID に属する複数の ScanResult のうち最大の RSSI を代表値として採用し、結果リストを RSSI の降順にソートしたうえで返却する[確認済: WifiUtils.kt:100-140, 139]。

整形後のリストは測定端末の画面上に BSSID・SSID・RSSI 等とともに表示され、測定者は任意の BSSID を選択することによって接続試行の対象とすることができる。一般的な測定手順としては、検出された全 BSSID を選択することが想定されている[推測: 周辺 AP 全件の通信可否を把握するという本研究の目的に適う既定の利用方法]。選択は画面操作によって確定するほか、自動スキャンモードが有効である場合には、検出された全 BSSID がそのまま測定対象として採用される[確認済: ConnectionMeasurementActivity.kt:311-332, 906-917]。

ステップ 3: 接続試行

本ステップにおいては、ステップ 2 で確定した測定対象 BSSID リストの各要素に対して、1 件ずつ接続試行が行われる。1 回のスキャンにおいて n 個の BSSID が検出された場合、本ステップは n 回の試行処理を直列に実行する。試行順序は、ステップ 2 において得られた順序、すなわち RSSI の降順である[確認済: WifiUtils.kt:139, SupplicantMeasurer.kt:174-186]。本順序の採用について、現時点では明示的な比較実験に基づく根拠を確認することができなかった[推測: RSSI が強い AP から優先的に試行することには、電波の弱い遠方 AP における長時間待機より先に近傍 AP の結果が得られる利点があるが、他順序との比較実験の記録は確認されない]。

1 件の接続試行は、「接続要求準備」と「接続要求の発行および状態観測」の 2 つのサブステップから構成される。

ステップ 3-1: 接続要求準備

IEEE 802.11 における接続開始手続きにおいては、端末が選択した AP のセキュリティ方式に応じて、認証フレームの種別・鍵交換フレームの有無・付随情報要素が変化する[要参考文献: IEEE 802.11-2020 §12 Security（および WPA3/SAE/OWE に関する改訂）]。そのため、接続要求を発行するに先立ち、対象 AP のセキュリティ分類に応じたパラメータ設定を要する。本機能においては、アプリから特定 AP への接続要求を発行する Android API である WifiNetworkSpecifier（android.net.wifi.WifiNetworkSpecifier.Builder）[要参考文献: Android Developers WifiNetworkSpecifier ドキュメント]に対し、セキュリティ分類ごとに異なるパスフレーズまたは認証構成を設定したうえで NetworkRequest を構築する。セキュリティ分類別の設定内容を表 1 に示す。[確認済: SupplicantMeasurer.kt:309-357]

WEP を対象外とする理由

WifiNetworkSpecifier は Android 10（API 29）において導入された、アプリから特定 AP への接続要求を発行するための API であるが、WifiNetworkSpecifier.Builder には WEP 鍵を設定するためのメソッドが定義されていない[要参考文献: Android Developers WifiNetworkSpecifier.Builder 公開メソッド一覧、および WifiConfiguration の非推奨化に関するリリースノート]。したがって本機能においては、WEP セキュリティのアクセスポイントを接続試行の対象外とし、最終状態を SKIPPED として記録する[確認済: SupplicantMeasurer.kt:315]。

EAP に対する接続試行の扱い

EAP を要求するアクセスポイントは、本来、正規の資格情報（証明書・ユーザ名・パスワード等）を保有しない限り、認証に成功することはない。本機能はこの資格情報を保有しないため、便宜的にダミーの WifiEnterpriseConfig を与える。認証の失敗はあらかじめ想定されるが、認証失敗までに観測されるサプリカント状態遷移（AUTHENTICATING への到達の有無等）を記録することが、本機能の目的である[確認済: SupplicantMeasurer.kt:335-349]。

ステップ 3-2: 接続要求の発行および状態観測

本研究においては、「接続試行」を、端末が特定 AP に対して IEEE 802.11 の認証・結合手続きの開始を要求する動作と定義する[要参考文献: IEEE 802.11-2020 §11.3（Authentication / Association procedures）]。Android 上においてこの要求を発行する API は ConnectivityManager.requestNetwork(request, callback, handler) である[要参考文献: Android Developers ConnectivityManager#requestNetwork ドキュメント]。本機能は、ステップ 3-1 において構築した NetworkRequest を第 1 引数に、結果通知を受ける NetworkCallback を第 2 引数として、この API を用いる[確認済: SupplicantMeasurer.kt:243-249]。

requestNetwork() の呼出し以降の処理は、以下に述べる手順によって進行する。

  1. Android フレームワーク層の ConnectivityManager が要求を受理し、Wi-Fi サブシステム（WifiService、HAL、Linux カーネル内の Wi-Fi ドライバ）を介して、ユーザ空間の認証モジュール wpa_supplicant へ、対象 AP への接続指示を伝達する[要参考文献: Android Open Source Project の Wi-Fi HAL アーキテクチャ資料および wpa_supplicant 公式ドキュメント]。
  2. wpa_supplicant は、対象 AP に対して認証フレーム・結合フレーム、および（WPA / WPA2 / WPA3 の場合）4-way ハンドシェイクフレームを順次送受信する[要参考文献: IEEE 802.11i / IEEE 802.11-2020 §12]。各段階の進行および終了は、Android の WifiManager.SUPPLICANT_STATE_CHANGED_ACTION ブロードキャストとして、SupplicantState 列挙値の形式によりアプリ側へ通知される[要参考文献: Android Developers SupplicantState ドキュメント]。本機能においては、SUPPLICANT_STATE_CHANGED_ACTION を IntentFilter に登録した BroadcastReceiver がこの通知を受信し、状態名と、測定開始時点からの経過時間（ms）とを 1 要素として、状態遷移の記録に追加する[確認済: SupplicantMeasurer.kt:98-108, 147-153]。通知される SupplicantState の種類を表 2 に示す。
  3. 接続試行の結末は、requestNetwork() に渡した NetworkCallback を通じても通知され得る。onAvailable(network) は、ネットワークが利用可能となったこと、すなわち Android プラットフォームが接続成立と判定した状態を意味する[要参考文献: Android Developers NetworkCallback#onAvailable ドキュメント]。本機能は onAvailable() のみを実装しており、本メソッドが発火した場合には、最終状態を NETWORK_AVAILABLE として記録し、待機を打ち切る[確認済: SupplicantMeasurer.kt:216-224]。なお、本機能はダミーの資格情報を用いるため、WPA / WPA2 / WPA3 の各 AP においては、認証失敗により onAvailable() が発火することは通常ない。Open および OWE のアクセスポイントにおいては認証自体が存在しないため、接続成立後に onAvailable() が発火し得る[推測: 実測ログを参照して確定するのが望ましい]。onUnavailable() は、現行実装において定義されていないため、発火した場合もアプリ側の処理に影響を及ぼすことはない[確認済: SupplicantMeasurer.kt:216-224]。

ステップ 4: ラベル付与（最終状態ラベルの決定）

設計の経緯

IEEE 802.11 の仕様書においては、認証・結合・4-way ハンドシェイクの各手続きが完了するまでの所要時間について、明示的な規定は示されていない[要参考文献: IEEE 802.11-2020 §11、§12 を精査のうえ確定]。また、測定端末に用いる Android プラットフォームの公式ドキュメントにおいても、SupplicantState の各遷移に要する時間の目安は示されていない[要参考文献: Android Developers SupplicantState ドキュメントの該当節]。したがって、1 件のアクセスポイントに対する接続試行がいつ終結するかは、事前には保証されない。

実運用上、onAvailable() やサプリカント状態遷移の終端が、必ずしもすべてのアクセスポイントにおいて観測されるとは限らない。かかる場合に無限の待機を行うことは、測定時間の観点から合理的ではないため、本機能においては、1 件のアクセスポイントに対する試行に上限時間（タイムアウト）を設ける方針を採用した。

タイムアウト値の設定根拠

タイムアウト値を定めるにあたり、「測定者が歩行移動する間に AP の電波範囲内に留まる時間」という観点から、以下の試算を行った。一般的な徒歩速度を 1.5 m/s（約 5.4 km/h）とするとき[要参考文献: 徒歩平均速度の出典]、接続試行の開始から 10 秒後には、測定者は AP の位置から約 15 m 離れた位置に達する計算となる。無線 LAN AP の実用的な電波到達範囲は数十 m 程度とされており[要参考文献: 無線 LAN AP の実用カバレッジに関する出典（例: IEEE 802.11 / Wi-Fi Alliance 技術資料）]、これを超過する距離・時間において接続試行を継続することの合理性は乏しいと判断した。この仮定に基づき、本機能においては、1 件のアクセスポイントに対する試行全体のタイムアウトを 10000 ms と定めた[確認済: SupplicantMeasurer.kt:30, 230]。

タイムアウト値の妥当性の検証

上記の値の妥当性を検証するため、サプリカント状態を受信するたびに、測定開始時点からの経過時間を記録する機能を用いて、実測を行った[確認済: SupplicantMeasurer.kt:98-108]。その結果、10 秒以内に認証手続きの結末（COMPLETED への到達、または認証失敗に伴う DISCONNECTED への復帰等）が観測されるアクセスポイントが多数存在することが確認された[要参考文献: 本研究内の実測結果を示す章節への参照（例: 「○章 実測結果」）]。

最終状態ラベルの必要性

1 回の接続試行においては、アクセスポイントにより (i) サプリカント状態遷移が 1 件も観測されない場合、(ii) 途中段階まで観測されるが COMPLETED に到達しない場合、(iii) COMPLETED に到達する場合が混在し得る。分析時に、アクセスポイント単位で試行結末を判別することを可能とするため、本機能においては、各試行の結末を一意に分類する文字列ラベルを独自に定義し、アクセスポイントごとに付与する。ラベルの決定規則を表 3 に示す。[確認済: SupplicantMeasurer.kt:267-287, 298-306]

ラベル値決定条件
SKIPPEDセキュリティ分類が WEP である場合、または BSSID から MacAddress が構築できず、接続試行自体が行われなかった場合。
REQUEST_FAILEDConnectivityManager.requestNetwork() の呼出し自体が例外を送出した場合。
NETWORK_AVAILABLENetworkCallback.onAvailable() が発火した場合（Android により接続成立と判定されたこと）。
AUTH_COMPLETEDサプリカント状態遷移列の末尾が COMPLETED である場合。
PRE_TIMEOUT_<前の状態>DISCONNECTED の受信による早期終了が生じた場合。<前の状態> とは、遷移列において DISCONNECTED の 1 つ前に現れる状態名を指す。
PRE_TIMEOUT_ASSOCIATEDASSOCIATED 受信時の早期終了モードが有効であり、かつ ASSOCIATED が受信された場合。
IDLE_<最も進んだ状態> / IDLE_NULL状態受信後の無変化タイマー（MODE1、3338 ms）の発火により終了した場合。遷移列が空である場合は IDLE_NULL。
TIMEOUT_<最も進んだ状態> / TIMEOUT_NULL全体タイムアウト（MODE1 は 10000 ms、MODE2 はユーザ指定値）が経過した時点において、上記のいずれの早期終了条件も成立しなかった場合。遷移列が空である場合は TIMEOUT_NULL。

「最も進んだ状態」は、DISCONNECTED < INACTIVE < SCANNING < AUTHENTICATING < ASSOCIATING < ASSOCIATED < FOUR_WAY_HANDSHAKE < GROUP_HANDSHAKE < COMPLETED の順序に基づき、遷移列から 1 つを選出するものとする。[確認済: SupplicantMeasurer.kt:298-306]

ステップ 5: データ送信

ステップ 3 およびステップ 4 を全アクセスポイントについて実行し終えた時点で、1 地点分の測定結果が確定する。測定者が n 地点における測定を終え、送信操作を行った場合、以下の処理が実行される。

  1. 各アクセスポイントの測定結果（サプリカント状態遷移列、最終状態ラベル、測定所要時間、接続要求 API 呼出し記録、および接続試行開始時刻の 5 項目）は、ビーコンスキャン機能から引き継いだ項目と併せて、1 件の JSON オブジェクトに整形され、端末内の保留データに追記される[確認済: SupplicantMeasurer.kt:289-295, ConnectionMeasurementActivity.kt:719-722, 925-933]。
  2. 自動スキャンセッションの終了時、本機能は、セッションを識別するラベルを java.text.SimpleDateFormat により "yyyy/MM/dd HH:mm~HH:mm <タイムアウトモード>" 形式の文字列として生成し、測定者に提示する。測定者は、これをそのまま採用するか、または任意の文字列に変更したうえで保存することが可能である[確認済: ConnectionMeasurementActivity.kt:587-625]。生成されたラベルは、保留データ内の当該セッションの識別情報として書き戻される。手動測定時においては、ラベルは空文字のまま保持される[確認済: ConnectionMeasurementActivity.kt:874, 972]。
  3. 送信モードが「測定直後の送信」である場合は測定完了時に、保留モードである場合は測定者による明示的な送信操作時に、保留データ内の未送信エントリは、HttpURLConnection を介して指定サーバ URL へ HTTP POST により順次送信される。送信に成功したエントリは保留データから削除され、失敗したエントリは端末内に保持される[確認済: ConnectionMeasurementActivity.kt:993-1034]。
