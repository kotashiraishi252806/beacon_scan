Design Specification

接続試行の設計仕様

WiFi Supplicant 状態測定アプリが「接続試行」を
どのような定義・ルールに基づいて実現しているかを、
第三者が理解できる形で記述したドキュメント。

対象コード：SupplicantMeasurer.kt ／ MainActivity.kt（getSecurity）
動作環境：Android API 30 ／ Motorola moto g31(w)
背景

なぜ AP をセキュリティ方式で分類するのか

接続試行の方法は、APのセキュリティ方式によって変わる。

前提：WiFi への接続には認証・暗号化の手順が必要であり、 その手順はセキュリティ方式（WPA2・WPA3・Open など）によってそれぞれ異なる。
問題：このアプリは「ダミーパスワード」で接続試行するため、 APのセキュリティ方式を事前に知らなければ正しい接続手順を組み立てられない。
結論：接続試行の前に、各 AP を セキュリティ方式に基づいていくつかのカテゴリに分類する必要がある。
情報源

セキュリティ方式はどこからわかるか

Android が提供する ScanResult.capabilities 文字列（capabilities_raw）から判定できる。

capabilities_raw とは
AP のビーコンフレームを Android（wpa_supplicant）が解析し、 アプリに渡す文字列。認証方式・鍵管理・暗号化方式が含まれる。
形式と例
形式：[認証-鍵管理-暗号化][...][ESS]
Open ：[ESS]
WPA2 ：[WPA2-PSK-CCMP][RSN-PSK-CCMP][ESS]
WPA3 ：[RSN-SAE-CCMP][ESS]　← "WPA3" の文字はない
WPA2/WPA3：[WPA2-PSK-CCMP][RSN-PSK+SAE-CCMP][ESS]
⚠ capabilities_raw には公式な仕様書がなく、 Android バージョンや端末・APのファームウェアによって表現が変わることがある。 アプリはこの文字列を直接解析して判定を行う。
判定上の注意点

WPA3 は capabilities_raw に "WPA3" と書かれない

WPA3-Personal の実装では、文字列 "SAE" が WPA3 の実質的な識別子になる。

旧ロジックの問題： "WPA3" という文字列の有無だけで判定すると、 SAE を使う WPA3 AP が "Open" に誤分類される。
実測データで 約 4,182 件 の誤分類が確認された。
誤分類の例
[RSN-SAE-CCMP][ESS] 　→ 旧判定：Open ✗　正しくは：WPA3
[RSN-SAE+FT/SAE-CCMP][ESS] 　→ 旧判定：Open ✗　正しくは：WPA3
修正： "SAE" を含むものは WPA3 と判定するようロジックを修正した。 この修正により "WPA3" の文字がなくても正しく WPA3 に分類される。
分類結果

判定の結果：6つのカテゴリ

capabilities_raw を上から順に評価し、最初にマッチした条件でカテゴリを決定する。

カテゴリ 判定条件（capabilities_raw に含む文字列） 対応する規格
WPA2/WPA3 "WPA2" かつ "SAE" を含む トランジションモード（両対応 AP）
WPA3 "WPA3" または "SAE" または "EAP_SUITE_B" を含む WPA3-Personal / Enterprise
WPA2 "WPA2" を含む WPA2-Personal / Enterprise
WPA "WPA" を含む WPA（初代）
WEP "WEP" を含む WEP（旧規格）
Open 上記いずれも含まない 認証・暗号化なし
判定は 上から順に評価 する。 "WPA2" は "WPA" を部分文字列として含むため、 WPA より先に WPA2 を評価しないと誤判定が起きる。 WPA2/WPA3 も同様に WPA2 より先に評価する。
接続試行ルール

カテゴリごとの接続試行方法

各カテゴリに対して、buildSpecifier() が異なる接続方法を組み立てる。

カテゴリ 接続試行の方法 測定フローへの影響
WEP 接続できない（Android API が WEP に非対応） SKIPPED　測定不可
Open 認証情報なしで接続試行 → 測定フローへ
WPA2 WPA setWpa2Passphrase("DUMMY_MEAS_12345") → 測定フローへ
WPA2/WPA3 setWpa3Passphrase("DUMMY_MEAS_12345") → 測定フローへ
WPA3 setWpa3Passphrase("DUMMY_MEAS_12345") → 測定フローへ
EAP 例外： capabilities_raw に "EAP" を含む AP はカテゴリに関わらず、 Enterprise 用の設定（PEAP + MSCHAPV2 + ダミー認証情報）を使用する。 これが分類と試行ルールが 1 対 1 に対応しない唯一の例外。
OS からの応答

接続試行中、OS から届く 3 種類の情報

アプリはこの 3 つの情報を組み合わせて最終状態を判定する。

① BroadcastReceiver — SupplicantState の遷移
wpa_supplicant の内部状態が変化するたびに通知が届く。 このアプリはその状態名を順番にリストへ記録していく。 これが supplicant_states（状態遷移リスト） となる。
② NetworkCallback — onAvailable / onUnavailable
OS がネットワーク接続を確認したとき onAvailable() が発火する。
OS が接続不可と判断したとき onUnavailable() が発火する。
いずれかが発火した時点で測定を即時終了する。
③ withTimeoutOrNull(15,000ms) — タイムアウト
① ② のいずれも発火しないまま 15 秒が経過した場合、 コルーチンのタイムアウトとして測定を強制終了する。
判定ロジック

3 つの情報を組み合わせて最終状態を決める

以下の条件を上から順に評価し、最初にマッチした結果を最終状態とする。

条件最終状態
onAvailable() が発火した COMPLETED
onUnavailable() が発火した　かつ　状態遷移リストが空 NOT_FOUND
状態遷移リストが空でない　かつ
最後の状態が DISCONNECTED / INACTIVE / SCANNING のいずれか 		FAILED_AT_<最終状態名>
状態遷移リストが空でない　かつ
最後の状態が上記以外（ASSOCIATING / FOUR_WAY_HANDSHAKE / COMPLETED 等） 		TIMEOUT_AT_<最終状態名>
15 秒タイムアウト　かつ　状態遷移リストが空　かつ　onUnavailable なし FAILED_AT_DIALOG_TIMEOUT
FAILED_AT_* と TIMEOUT_AT_* は、最後の状態名を suffix に付けた動的な文字列。 どちらになるかは「最後の状態が切断系か否か」だけで決まり、 15秒経過したかどうかは判定に関係しない。

補足

CANCELLED は測定フロー外の要素

停止ボタンによる中断は接続試行の分類体系とは独立しており、研究上の分析対象に含めない。

停止ボタンを実装した理由（2つ）：
① 多数の AP に連続接続試行すると AP 側に攻撃と認識されるリスクがあるため、途中で中断できる手段が必要だった。
② 駅など AP 数が多い場所での現地テスト時に、全件測定では時間がかかりすぎるため。
なぜ分析対象から除外するか：
CANCELLED は AP の性質や OS の応答とは無関係に、ユーザーの任意操作で発生する。 同じ AP でも停止ボタンを押したかどうかで結果が変わるため、 再現性・決定論性がなく、測定結果として扱えない。
分類体系における位置づけ
測定フロー内（分析対象）：17 種類
　　G1 技術的制約 ／ G2 成功 ／ G3 AP非到達 ／ G4 明示的失敗 ／ G5 タイムアウト
測定フロー外（分析対象外）：CANCELLED（停止ボタンによる中断）
