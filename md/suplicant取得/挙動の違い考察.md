# Supplicant測定中に見られる挙動の違い　考察

## 観察された3パターン

| パターン | 見た目 | 原因 |
|---------|--------|------|
| A | ポップアップが全く表示されない | セキュリティ種別によるSKIPPED、またはOSが即座にonUnavailable |
| B | ダイアログが一瞬出てすぐ消え、エラーになる | OSがBSSIDを検出できずonUnavailableを即時発火 |
| C | ダイアログが出て、「接続」を押した後にエラー | 想定通りの接続試行→認証失敗フロー |

---

## パターンA：ポップアップが全く表示されない

### 原因1：SKIPPED（EAP/WEP）

`buildSupplicantSpecifier()` が `null` を返すとき、`requestNetwork()` 自体が呼ばれない。

- `security == "WEP"` → `null` を返す
- `capabilities` に `"EAP"` を含み `"OWE"` を含まない（Enterprise認証）→ `DUMMY_USER`/`DUMMY_PASSPHRASE` でビルドを試みるが、`builder.build()` が例外を投げると `null`

この場合 `measureSupplicantForAp()` は即座に `supplicantFinalState = "SKIPPED"` で返る。

### 原因2：OSが即時 onUnavailable

`requestNetwork()` は呼ばれているが、AndroidのConnectivityスタックが「このBSSIDは接続不能」と即時判断して `onUnavailable()` をダイアログUI表示より前に発火させる場合。BSSIDがOSの内部スキャンキャッシュに存在しない、または電波が極端に弱い場合に起きやすい。

ダイアログは画面に出ないか、出ても人間が認識できない数十ms単位で消える。

---

## パターンB：ダイアログが一瞬出てすぐ消え、エラーになる

`requestNetwork()` の呼び出しによりAndroidシステムが「接続しますか？」ダイアログを表示する。しかし：

- APの電波が弱い / OSのスキャン結果が古くてBSSIDが見つからない
- Androidが接続不能と判断するまでに1〜数秒かかる

その間だけダイアログが表示され、`onUnavailable()` が発火するとダイアログが強制的に消える。

**コード上の動作：**
1. Phase1（`withTimeoutOrNull(15秒)`）が `onUnavailable()` で即時終了
2. `finalState` は `"NOT_FOUND"` のまま
3. Phase2（8秒）に進み、Supplicant状態遷移を待つ
4. 遷移がなければ → `"NOT_FOUND"` で終了
5. 遷移があれば → `"FAILED_AT_<最終状態>"` または `"TIMEOUT_AT_<最終状態>"`

ユーザーには「押すタイミングがない」ように見える。

---

## パターンC：想定通りの挙動（ダイアログを押したあとエラー）

1. `requestNetwork()` → Androidがダイアログを表示
2. APがOSのスキャン結果に存在し、電波が十分 → ダイアログが保持される
3. ユーザーが「接続」を押す → AndroidがBSSIDへの接続を試みる
4. `SUPPLICANT_STATE_CHANGED_ACTION` でSCAN / ASSOCIATING / ASSOCIATED 等が順次発火 → `supplicantTransitions` に記録
5. `onUnavailable()` または `onAvailable()` が発火してPhase1が終了
6. Phase2（8秒）でSCOMPLETED待ち → タイムアウトまたはFAILED状態で終了

このパターンが「測定できている」状態。接続には失敗するが、どこの状態で失敗したかが `supplicant_final_state` と `supplicant_states` に記録される。

---

## まとめ：挙動を決める主な要因

| 要因 | 影響 |
|------|------|
| セキュリティ種別（WEP/EAP） | `buildSupplicantSpecifier()` が null → SKIPPED、ダイアログなし |
| BSSIDがOSのスキャンキャッシュに存在するか | NoならonUnavailableが即時発火 → ダイアログなし or 一瞬 |
| 電波強度・接続可能性 | 弱いほどonUnavailableが早く発火 → ダイアログが短命 |
| APが接続試行を受け付けるか | 認証フェーズに進めるかどうか → SuperticantTransitionsの深さに影響 |

---

## 補足：タイムアウト定数

```
DIALOG_TIMEOUT_MS = 15,000 ms（Phase1の最大待機時間）
AUTH_TIMEOUT_MS   =  8,000 ms（Phase2の最大待機時間）
```

Phase1が15秒以内に終わらなかった場合は `"FAILED_AT_DIALOG_TIMEOUT"` となる。
（OSがダイアログをキャンセルしたが `onUnavailable()` も呼ばれなかった極めてまれなケース）
