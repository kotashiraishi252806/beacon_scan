# システム改変：接続試行処理の変更

日付：2026-07-27  
対象ファイル：`app/src/main/java/com/example/beacon_scan/SupplicantMeasurer.kt`

---

## 1. 概要

AP1台あたりのSupplicant測定処理を、現状の**Phase1（15秒）＋Phase2（8秒）の2段構成**から、**単一待機（15秒）の1本構成**へ変更する。

BroadcastReceiverが最初のSupplicant状態イベントを受けてPhase1を終了させるロジック（`isFirst`）を廃止し、terminal state（COMPLETED / 認証後DISCONNECTED）またはOSからの通知（`onAvailable` / `onUnavailable`）が届いた時点でのみコルーチンを再開する設計に統一する。

---

## 2. 変更に至る経緯

### 当初の設計意図

Phase1は「ユーザーがOSの接続確認ダイアログのOKを押すまで待つ」フェーズとして設計された。ダイアログを押してOSが動き出したことを確認してからPhase2（認証シーケンスの記録）へ移行する、という2段階の想定だった。

### 実測で判明した実態（7/24 テスト結果より）

2026-07-24に実施した52AP・約5分間の実測（`修正後.json`、`7-24計算フロー推測.md`）で、以下が判明した。

- **ダイアログはOSが表示するかしないかを決定する**。アプリはrequestNetwork()を呼ぶだけであり、ダイアログ表示の有無・タイミングはOSの制御下にある。
- 実測28件のうち、ユーザーがダイアログを操作したケースは一部に限られ、**ダイアログなしにBroadcastReceiverへSupplicant状態が届くケースが多数**（経路B: 17件、経路C: 3件 等）存在した。
- 「Phase1 = ダイアログ待ち」「Phase2 = 認証待ち」という区分の前提が実態と乖離していた。

### 方針決定（7/24）

Phase1/Phase2の区別をやめ、AP1台の測定タイムアウトを15秒の単一待機に統一する方針を決定した。詳細フローは `md/順次接続試行シーケンス図ver2.md` に記録済み。

---

## 3. 変更案（現状 → 提案）

### 変更①：BroadcastReceiver の `isFirst` ロジック

**現状：**
```kotlin
val isFirst = supplicantTransitions.isEmpty()
supplicantTransitions.add(state.name)
val cont = supplicantContinuation ?: return
if (!cont.isActive) return
if (isFirst) {
    cont.resume(Unit)  // 最初のイベントで無条件に resume → Phase1 終了
    return
}
when (state) {
    SupplicantState.COMPLETED -> cont.resume(Unit)
    SupplicantState.DISCONNECTED -> {
        if (supplicantTransitions.any {
            it == "ASSOCIATED" || it == "FOUR_WAY_HANDSHAKE" || it == "GROUP_HANDSHAKE"
        }) cont.resume(Unit)
    }
    else -> {}
}
```

**提案：**
```kotlin
supplicantTransitions.add(state.name)
val cont = supplicantContinuation ?: return
if (!cont.isActive) return
// isFirst ロジック削除。terminal state のみ resume
when (state) {
    SupplicantState.COMPLETED -> cont.resume(Unit)
    SupplicantState.DISCONNECTED -> {
        if (supplicantTransitions.any {
            it == "ASSOCIATED" || it == "FOUR_WAY_HANDSHAKE" || it == "GROUP_HANDSHAKE"
        }) cont.resume(Unit)
    }
    else -> {}
}
```

### 変更②：`measureForAp()` の待機構造

**現状（2段構成）：**
```kotlin
// Phase1：最大15秒
val phase1Completed = withTimeoutOrNull(DIALOG_TIMEOUT_MS) {
    suspendCancellableCoroutine<Unit> { cont ->
        supplicantContinuation = cont
        supplicantCallback = cb
        cont.invokeOnCancellation { ... }
        connectivityManager.requestNetwork(request, cb)
    }
}

// Phase1 タイムアウト → FAILED_AT_DIALOG_TIMEOUT で即 return
if (phase1Completed == null) {
    return ap.copy(supplicantFinalState = "FAILED_AT_DIALOG_TIMEOUT", ...)
}

// onAvailable / onUnavailable / stopRequested → 早期 return
if (finalState == "COMPLETED" || unavailableFired || stopRequested) {
    return ap.copy(...)
}

// Phase2：最大8秒
withTimeoutOrNull(AUTH_TIMEOUT_MS) {
    suspendCancellableCoroutine<Unit> { cont ->
        supplicantContinuation = cont
        cont.invokeOnCancellation { supplicantContinuation = null }
    }
}

// 後片付け＋finalState確定
```

**提案（単一待機）：**
```kotlin
// 単一待機：最大15秒
// onAvailable / onUnavailable / terminal state のいずれかで早期終了
withTimeoutOrNull(DIALOG_TIMEOUT_MS) {
    suspendCancellableCoroutine<Unit> { cont ->
        supplicantContinuation = cont
        supplicantCallback = cb
        cont.invokeOnCancellation { ... }
        connectivityManager.requestNetwork(request, cb)
    }
}

// 後片付け＋finalState確定
```

途中の早期 return ブロック2つ（`phase1Completed == null` の判定、`finalState == "COMPLETED" || ...` の判定）がまるごと不要になる。

---

### 変更③：定数とエラー種別

**現状：**

| 定数 | 値 | 用途 |
|---|---|---|
| `DIALOG_TIMEOUT_MS` | 15,000ms | Phase1 タイムアウト |
| `AUTH_TIMEOUT_MS` | 8,000ms | Phase2 タイムアウト |

エラー種別に `FAILED_AT_DIALOG_TIMEOUT`（Phase1が15秒超えた場合）が存在する。

**提案：**

| 定数 | 値 | 用途 |
|---|---|---|
| `DIALOG_TIMEOUT_MS` | 15,000ms | 単一タイムアウト（名称は変更してもよい） |
| `AUTH_TIMEOUT_MS` | ~~8,000ms~~ | **削除** |

`FAILED_AT_DIALOG_TIMEOUT` はなくなる。15秒タイムアウト時は：
- `supplicantTransitions` が空 → `NOT_FOUND`
- `supplicantTransitions` が非空 → `TIMEOUT_AT_<最終状態>`

---

## 4. 期待できる効果

### 設計の単純化
- `suspendCancellableCoroutine` の呼び出しが2回→1回になり、コルーチンの再開経路が整理される。
- `isFirst` フラグ、`phase1Completed` の null チェック、中間の早期 return ブロックが削除でき、処理フローが直線的になる。

### 測定の実態への適合
- 「ダイアログを押してから認証を記録する」という前提を捨て、OSが何を返してきても正しく記録できる構造になる。
- Phase1でBroadcastReceiverの最初のイベントを受けて即 resume していた挙動がなくなるため、認証シーケンスの全列（ASSOCIATING→ASSOCIATED→FOUR_WAY_HANDSHAKE→DISCONNECTED 等）を取りこぼさずに記録できる。

### AP1台あたりの最大測定時間の短縮
- 現状：Phase1（最大15秒）＋Phase2（最大8秒）= 最大23秒
- 提案：単一15秒
- terminal state が早期に届けば15秒未満で完了するため、合計測定時間が短縮される。

---

## 5. 予想できるリスク

### terminal state が来ないケースへの影響
現状のPhase2は「認証シーケンス途中（ASSOCIATING / ASSOCIATED / FOUR_WAY_HANDSHAKE 等）で止まっているAPに対して最大8秒待つ」役割を持っていた。単一15秒に変えても、これらのAPはタイムアウトまで待つことになるため動作上の問題はないが、**旧Phase2の8秒で早期終了していたケースが15秒まで待つようになる**可能性がある。

→ 実測データ（経路C: `TIMEOUT_AT_ASSOCIATED` 3件・8秒タイムアウト、経路D: `TIMEOUT_AT_FOUR_WAY_HANDSHAKE` 2件・8秒タイムアウト）が該当する。これらは最大15秒まで伸びる。

### `FAILED_AT_DIALOG_TIMEOUT` の消滅による後方互換性
サーバー側やデータ分析ツールが `FAILED_AT_DIALOG_TIMEOUT` という値を想定している場合、変更後に値が出現しなくなる。既存の保存済みデータとの種別混在が生じる。

### BroadcastReceiver の最初のイベントを受け取らなくなることの副作用
現状のPhase1は「OSが動き出したかどうか」の確認として機能していた。単一待機ではこの確認がなくなる。OSが全く動き出さない（BroadcastReceiverにも`onUnavailable`にも何も来ない）ケースは15秒タイムアウトまで待つことになり、これは現状と同じ挙動のため問題はない。
