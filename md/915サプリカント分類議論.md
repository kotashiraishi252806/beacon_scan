**目的**: test32.csv の 109 パターン（遷移記録なしを除く）をクラスタリングし、AP 管理者への実測ベースの支援につなげる

test32.csv の 109 パターンをそのまま AP 管理者に提示しても「支援より混乱を招く」状態。

## 議題 1：理論値の改訂（4 → 7 パターン）【確定】

### 方針決定事項

現 P4（HTML スライド）の「セキュリティ方式別遷移パターン 4 種」は理論値として不適当と判断。  
先行研究の 5 認証方式 × 成功・失敗 = 7 パターンを分類基準とする（WPA-PSK/WPA2-PSK 成功は統合）。

### 確定した 7 理論パターン

> 表記注記：先頭の `DISCONNECTED, SCANNING` はカンマ区切りで「どちらの状態からも開始しうる」を示す（実測では INTERFACE_DISABLED 始まりが最多だが、理論値では前処理を省略して表記）。

| # | 方式・結果 | 理論遷移パターン |
|---|---|---|
| 1 | Open（接続成功） | `DISCONNECTED, SCANNING → ASSOCIATING → COMPLETED` |
| 2 | WPA-PSK / WPA2-PSK（成功） | `DISCONNECTED, SCANNING → ASSOCIATING → ASSOCIATED → FOUR_WAY_HANDSHAKE → GROUP_HANDSHAKE → COMPLETED` |
| 3 | WPA-PSK / WPA2-PSK（失敗） | `DISCONNECTED, SCANNING → ASSOCIATING → ASSOCIATED → FOUR_WAY_HANDSHAKE → DISCONNECTED` |
| 4 | WPA2-EAP（成功） | `DISCONNECTED, SCANNING → ASSOCIATING → ASSOCIATED → FOUR_WAY_HANDSHAKE → COMPLETED` |
| 5 | WPA2-EAP（失敗） | `DISCONNECTED, SCANNING → ASSOCIATING → ASSOCIATED → DISCONNECTED` |
| 6 | WPA3-SAE（成功） | `DISCONNECTED, SCANNING → ASSOCIATING → FOUR_WAY_HANDSHAKE → GROUP_HANDSHAKE → COMPLETED` |
| 7 | WPA3-SAE（失敗） | `DISCONNECTED, SCANNING → ASSOCIATING → DISCONNECTED` |

**注記1（#1 Open と ASSOCIATED）**：先行研究の理論値に従い ASSOCIATED を含めない。実測では ASSOCIATING → ASSOCIATED → COMPLETED を経由するパターンが多いが、それは実測値として別途記録する（理論値とは区別）。

**注記2（#2 WPA-PSK と WPA2-PSK の統合）**：状態遷移だけでは両者を区別できないため、1 パターンに統合。AP のセキュリティ分類（`getSecurity()` の返値）を別途参照して区別する。

**注記3（#4 WPA2-EAP 成功の GROUP_HANDSHAKE なし）**：解釈 B で確定。EAP 成功は `FOUR_WAY_HANDSHAKE → COMPLETED`（GROUP_HANDSHAKE なし）。GROUP_HANDSHAKE の有無が PSK 成功（#2）と EAP 成功（#4）の遷移上の判別指標となる。

## 議題 2：109 パターンのクラスタリング手法

### 正規化ルール（分類前の前処理）

1. **OS 前処理プレフィックスの扱い**：先頭に `INTERFACE_DISABLED → DISCONNECTED →` が付く場合、これは OS 内部の前処理であり意味的なシーケンスに含めない（コア部分のみで照合）
2. **SCANNING 省略ルール**：中間に SCANNING が挿入されているパターンは、SCANNING を取り除いたシーケンスが理論値に一致する場合、そのパターンに分類する。ただし「SCANNING 介在あり」を属性として付記する

### クラスター案（暫定）

| クラスター | 定義 | 実測例 | AP 管理者への示唆 |
|---|---|---|---|
| **A：理論パターン照合可** | 正規化後に 9 パターンのいずれかに一致 | #2(221件), #3(48件), #13(8件)... | セキュリティ方式・認証の診断が可能 |
| **B：繰り返しリトライ系** | ASSOCIATING → DISCONNECTED のループが複数回繰り返される | #4(18件), #16(6件)... | AP に起因しない可能性（OS 内部競合・API35 固有）。AP への示唆は限定的 |
| **C：SCANNING 省略で照合可** | SCANNING 除去後に理論値一致 | #21(4件), #22(3件)... | クラスター A に準じた示唆。SCANNING 挿入の経緯は端末・API 依存 |
| **D：照合不可（途中停止）** | 正規化後も理論値に一致しない | #6(ASSOCIATING止まり 16件), #26(ASSOCIATED止まり 3件)... | タイムアウト打ち切り。測定条件（電波・混雑）の問題 |

### 繰り返しリトライ群（クラスター B）の詳細

核として抽出できる繰り返し単位：`ASSOCIATING → DISCONNECTED`

- 形式上は理論値 #7（WPA3-SAE 失敗）と一致するが、対象 SSID が Open 系（SENDAI_free_Wi-Fi / TOHOKU_United_Free_Wi-Fi）であり意味的に矛盾
- 端末：motorola edge 40 neo（API35）に集中
- 原因仮説：`requestNetwork()` による接続試行が OS の既存接続と競合して失敗を繰り返している

**判断ルール**：「核の形が理論値に一致しても、AP のセキュリティ方式と食い違う場合はクラスター B（OS 内部要因）として分ける」を分類ルールに明示する。

## 議題 3：遷移記録なし（278 件・33.9%）の扱い

109 パターンのクラスタリング対象外とした経緯はあるが、全体フレームワーク内での位置づけが未決定。

**特性**：
- EAP 系 AP（0000tohtech, Wi2eap, 0000softbank, eduroam）× API34/35 端末の組み合わせで多発
- `onUnavailable` も来ない → OS が接続試行を一切行っていない
- Open AP（SENDAI_free_Wi-Fi）でも一部発生

**未決の問い**：

> 遷移記録なしは「AP の特性（EAP × API34/35 の組み合わせ）を反映している」として AP 管理者に伝える情報になりうるか？それとも測定限界として除外するか。

| 案 | 位置づけ |
|---|---|
| A：独立クラスター | 「OS が試行しなかった」として明示。AP 管理者への示唆：「端末の API バージョンによっては接続試行が発生しない可能性」 |
| B：クラスタリング外・測定課題として別記 | 本分類の対象外と明示し、測定手法改善の課題として切り出す |

## 参考：8 種類のサプリカント状態（実測で観測されたもの）

| 状態 | 実測での役割 |
|---|---|
| `INTERFACE_DISABLED` | OS 内部リセット。前処理として最頻出 |
| `DISCONNECTED` | 初期・切断後・失敗後に出現 |
| `SCANNING` | AP 探索。中間挿入としても出現 |
| `ASSOCIATING` | AP への接続要求。パターン先頭になりうる |
| `ASSOCIATED` | Layer2 確立。ここまで来れば AP は物理的に存在 |
| `FOUR_WAY_HANDSHAKE` | PTK 導出・交換 |
| `GROUP_HANDSHAKE` | GTK 配布 |
| `COMPLETED` | 鍵交換完了・暗号通信可能 |

> `AUTHENTICATING` はスライド P3 に記載があるが実測では未観測。この議論では P3 の注記扱いとし、分類基準には含めない。
