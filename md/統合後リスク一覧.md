# Phase1/Phase2統合後のリスク一覧

対象：`SupplicantMeasurer.kt` の `measureForAp()` を、Phase1（15秒）＋Phase2（8秒）の2段構成から単一待機（15秒）の1本構成へ変更する案（`7-27-システム改変：接続試行処理の変更.md` 記載）に対するリスク評価。

---

## 1. 停止ボタン誤記録（CANCELLEDが記録されなくなる）

### 何が起きるか
測定中に停止ボタンを押した瞬間、その時点で処理中だったAP1件の結果が「CANCELLED」ではなく、NOT_FOUNDやTIMEOUT_AT_〜など別のラベルで記録されてしまう。本来は「途中で打ち切られたデータ」であるにもかかわらず、「正常に測定が完了したデータ」であるかのように見えてしまう。

### 原因
現状のコードでは、`stopRequested`（停止ボタンが押されたか）の判定は、Phase1とPhase2の間にある中間の早期returnブロックでのみ行われている。

```kotlin
if (finalState == "COMPLETED" || unavailableFired || stopRequested) {
    return ap.copy(
        supplicantFinalState = when {
            stopRequested && finalState != "COMPLETED" -> "CANCELLED"
            unavailableFired -> "NOT_FOUND"
            else -> finalState
        },
        ...
    )
}
```

7/27のmd内の統合案では、この中間ブロックを「不要になる」として丸ごと削除する提案になっている。削除後に残る「後片付け＋finalState確定」ブロックは、届いたsupplicant状態の遷移だけを見て名前を決めており、`stopRequested`を一切参照していない。そのため、停止ボタンが押されたという事実がラベルに反映されなくなる。

なお、停止ボタンを押した後まだ着手していない残りのAPは、`measureAll()`のループ側で別途CANCELLED処理されるため影響を受けない。影響を受けるのは「押した瞬間に処理中だった1件」のみ。

### 対策
中間ブロックを丸ごと削除するのではなく、統合後の「finalState確定」処理の中で`stopRequested`を明示的にチェックする一行を残す。フェーズ構成を元に戻す必要はない。

---

## 2. NOT_FOUND判別喪失（onUnavailableと15秒沈黙の区別が消える）

### 何が起きるか
今までは「OSがすぐに『無理』と教えてくれたケース（onUnavailable発火）」と「OSが15秒間まったく反応しなかったケース（真の沈黙）」を、それぞれ別の名前（NOT_FOUND / FAILED_AT_DIALOG_TIMEOUT）で区別して記録していた。統合後は、supplicant状態の記録が空であれば両方とも同じ"NOT_FOUND"という名前になり、データ上区別がつかなくなる。

### 原因
リスク1と同じ中間ブロックが原因。`onUnavailable()`が発火したかどうかを示す`unavailableFired`フラグは、この中間ブロックでのみ最終ラベルに反映されていた。ブロックが削除されると、`unavailableFired`は裏で記録され続けるものの、最終的な名前を決める処理から一切参照されなくなる。

所要時間（`supplicantElapsedMs`）を見れば、onUnavailableがすぐ発火したケース（数秒程度）と真の15秒沈黙（15000ms前後）は事後的に区別できるが、ラベル名だけでは区別できなくなる。

### 対策
リスク1と同様、最終ラベルを決める処理で`unavailableFired`を参照し、「onUnavailable発火によるNOT_FOUND」と「15秒沈黙によるタイムアウト」を別名で記録する。

## 3. 待機時間増加（8秒だったものが最大15秒に伸びる）

### 何が起きるか
認証シーケンスの途中（ASSOCIATED、FOUR_WAY_HANDSHAKEなど、terminal stateに該当しない状態）で止まったAPは、今までPhase2の8秒でタイムアウトしていたが、統合後は単一の15秒タイムアウトまで待つことになる。

### 原因
Phase2（8秒）という短いタイムアウトの枠自体がなくなり、全ての待機が15秒の枠に統一されるため。

実測データ（7/24、52AP・約5分間の測定のうち解析対象28件）では、該当するケースが5件確認されている。
- 経路C（TIMEOUT_AT_ASSOCIATED、FT/PSK対応APでASSOCIATEDのまま停滞）：3件
- 経路D（TIMEOUT_AT_FOUR_WAY_HANDSHAKE、4WAYハンドシェイク途中で停滞）：2件

28件中5件（約18%）が該当し、AP52台規模のスキャン全体では、これらのAPそれぞれで待機時間が約7秒ずつ伸びることになる。

### 対策
これは設計変更（測定の網羅性・正確性を優先する）によって意図的に許容するトレードオフであり、7/27のmd内でもリスクとして既に認識されている。速度を重視する場合は、単一タイムアウトの秒数を15秒より短く再設定することも検討可能。

## 4. 命名不整合（TIMEOUT_AT_COMPLETEDという紛らわしい名前）

### 何が起きるか
wpa_supplicant側（Wi-Fiチップの認証処理）ではCOMPLETED（認証完了）まで到達しているにもかかわらず、ConnectivityManager側の`onAvailable()`（Android全体としての接続確定通知）が来なかった場合、結果のラベルが"TIMEOUT_AT_COMPLETED"となる。「タイムアウトした」という名前だが、実態は「認証は完了しているが、OS側の最終確定通知だけが来なかった」状態であり、名前と実態が食い違っている。

### 原因
統合案によって新たに生じる問題ではなく、既存の`measureForAp()`の最終ラベル決定処理にもとから存在する挙動であり、統合後もそのまま引き継がれる。

```kotlin
if (finalState != "COMPLETED") {
    finalState = if (transitions.isNotEmpty()) {
        val last = transitions.last()
        if (last == "DISCONNECTED" || last == "INACTIVE" || last == "SCANNING") {
            "FAILED_AT_$last"
        } else {
            "TIMEOUT_AT_$last"   // last が "COMPLETED" の場合もここに入る
        }
    } else {
        "NOT_FOUND"
    }
}
```

`finalState`（onAvailableの発火有無で決まる変数）が"COMPLETED"にならなかった場合、supplicant状態の最後の遷移が何であれ"TIMEOUT_AT_<状態名>"という名前が付けられる。最後の遷移がたまたま"COMPLETED"だった場合、この名前が"TIMEOUT_AT_COMPLETED"となり、紛らわしい表記が生まれる。

実測データ（7/24）では経路E（4件、elapsed約1.2〜1.4秒）がこれに該当する。所要時間が短い（8秒や15秒のタイムアウト境界ではない）ことからも、これが真のタイムアウトではないことが確認できる。

### 対策
最後の遷移状態が"COMPLETED"の場合を専用の分岐として切り出し、「supplicant側は完了したが、OS側の確定通知（onAvailable）が来なかった」ことを表す専用のラベル（例："AUTH_COMPLETED_NOT_CONFIRMED"）を付ける。必要であれば、`supplicantFinalState`とは別に「onAvailableが来たか」を示す真偽値フィールドを追加で記録すると、後の分析がしやすくなる。

---

## まとめ

| No. | リスク | 統合が直接の原因か | 深刻度 |
|---|---|---|---|
| 1 | 停止ボタン誤記録 | 統合案（中間ブロック削除）が直接の原因 | 高（データの信頼性に関わる） |
| 2 | NOT_FOUND判別喪失 | 統合案（中間ブロック削除）が直接の原因 | 中（elapsed_msで事後的に代替可能） |
| 3 | 待機時間増加 | 統合の意図的なトレードオフ | 低（速度低下のみ、データ欠損なし） |
| 4 | 命名不整合 | 既存の問題（統合とは無関係、そのまま残る） | 低〜中（分析時に誤解を招く） |

リスク1・2はいずれも同じ中間ブロック（`if (finalState == "COMPLETED" || unavailableFired || stopRequested)`）の削除に起因するため、削除するのではなく最終ラベル決定処理に`stopRequested`と`unavailableFired`のチェックを残すことで、フェーズ構成を変えずに両方とも解消できる。
