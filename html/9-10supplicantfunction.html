beacon_scan アプリ ／ 無線LAN環境測定プロジェクト
1

何を実現しようとしているのか

目的

無線LANは広範囲をカバーできる反面、どこで使えてどこで使えないかを把握することが難しい。 電波が届いていてもサービスが利用できるとは限らず、AP設置者はサービス利用可否を網羅的に把握する手段を持っていない。 本研究はこの課題を解決するAP設置者向けの支援システムの構築を目指している。

手段としてのSupplicant取得

サービス利用可否の指標として Supplicant状態遷移 を採用する。 Supplicantは認証処理（データリンク層までの接続確立状況）を把握できるため、 「電波は届いているが繋がらない」という状況の原因を特定する指標として妥当である。

2

実装アプローチ

基本構造：requestNetwork() による接続試行

Android標準API ConnectivityManager.requestNetwork() を用いて、スキャンで検出した各APへの接続をOSに依頼する。アプリはOSへのトリガーを呼ぶだけであり、実際の接続処理・ダイアログ表示はすべてOS側が担当する。

アプリが制御できること

  • requestNetwork() の呼び出しタイミング
  • タイムアウト時間の設定（現在 15 秒）
  • Supplicant状態の受信・記録
  • AP単位のスキップ判定（WEP等）

アプリが制御できないこと

  • ダイアログの表示・非表示の判断
  • 実際のWi-Fiフレーム送受信・認証処理
  • Supplicant状態の発火タイミング
  • onAvailable / onUnavailable の呼び出し

AP別の処理フロー

セキュリティ処理理由
WEP 即時 SKIPPED 現代環境では実質廃止。接続試行そのものを省略。
EAP（Enterprise） ダミー認証情報で試行 証明書不要な形式でビルド可能な場合のみ。それ以外は SKIPPED。
WPA2 / WPA3 / WPA2+WPA3 通常試行（最大 15 秒） パスワード不一致を意図的に起こし、認証フェーズの記録が目的。

現時点でできていること

✓ AP単位の順次接続試行

スキャンで検出された全APに対して1台ずつ順番に requestNetwork() を呼び出し、Supplicant状態遷移を記録する処理が動作している。

✓ Supplicant状態遷移の記録

接続試行中にOSから受け取ったSupplicant状態（DISCONNECTED・ASSOCIATING・FOUR_WAY_HANDSHAKE 等）をすべて時系列で記録し、JSONとして出力できている。

✓ 最終状態のラベリング

接続試行の結果を以下のラベルで自動的に分類している。

COMPLETED FAILED_AT_<状態名> TIMEOUT_AT_<状態名> FAILED_AT_DIALOG_TIMEOUT TIMEOUT_AT_COMPLETED SKIPPED CANCELLED

✓ セキュリティ方式別の自動判定・スキップ

WEPは接続試行を即時スキップ。EAPはダミー認証情報でビルドを試みる。セキュリティ方式（WPA2/WPA3/WPA2+WPA3等）は capabilities_raw 文字列からパースして自動分類。

✓ 測定結果のサーバー送信

各AP の supplicant_states・supplicant_final_state・supplicant_elapsed_ms を含む完全なスキャン結果をJSON形式でサーバーにPOSTできている。

✓ 測定中断（CANCELLED）対応

ユーザーが測定中に停止ボタンを押した場合、処理中のAPを CANCELLED、未着手のAPも CANCELLED としてラベリングし、中断を明示的に記録できている。

課題

課題 1：測定時間が長すぎる 深刻度：高

現状： 57AP で約 550秒（9分10秒）。AP1台あたり平均 9.6秒。

影響：

  • 1地点の測定に約 9〜10分 かかるため、6地点で約 1時間。
  • 10m メッシュ・100m四方（100地点）の測定に単純計算で 約16時間以上 必要。実用的な野外測定に耐えない。

原因： AP 27台（48%）が 15秒タイムアウトに到達している。特に FAILED_AT_DIALOG_TIMEOUT の 20台（合計 300秒）が主な時間消費源。

検討中の対策：

  • タイムアウト短縮（15s → 5s）：実装コスト低。約270秒削減（550s → 280s）が見込める。TIMEOUT_AT_COMPLETED（実質接続成功）が平均1.4秒で完了しているため、5秒でも測定データの品質は維持できると考えられる。
  • 並列化（2〜3AP同時試行）：実装コスト高。理論上さらに1/2〜1/3に短縮できるが、requestNetwork() 多重呼び出し時のOS挙動が未検証。
  • EAPスキップ拡大：EAP系APは常にダミー認証で失敗し、かつ長時間かかる。スキップ対象に加える選択肢あり。

課題 2：FAILED_AT_DIALOG_TIMEOUT の原因が不明 深刻度：高

現状： 57台中 20台（35%）が 15秒間 Supplicant状態が一切発火せず、何の情報も取得できないまま終了する。

観察事実：

  • supplicant_states が空（[]）
  • 画面上のダイアログも表示されない（パターンJ）
  • BroadcastReceiver にも NetworkCallback にも 15秒間何も届かない

仮説： OSがスキャンキャッシュでBSSIDを確認できない、または電波が弱いためConnectivityスタックが即時応答すらしない状態と推定されるが、APIから確認する手段がない。

課題点： これらのAPについては接続試行が実際にOSに受け付けられたのかすら不明。測定データとして「15秒待ったが何も分からなかった」という記録しか残せない。

課題 3：TIMEOUT_AT_COMPLETED という命名の不整合 深刻度：中

現状： 57台中 12台（21%）が TIMEOUT_AT_COMPLETED と記録されている。

問題： この名前は「タイムアウトした」という意味に読めるが、実態は wpa_supplicant側の認証は COMPLETED まで到達している（= 認証処理としては成功）にもかかわらず、Android ConnectivityManager側の最終確定通知（onAvailable）が届かなかっただけ。

実測値： 平均 1.4秒で完了しており、15秒タイムアウトとは無関係。名前から「認証失敗」と誤読される懸念がある。

対策案： AUTH_COMPLETED_NOT_CONFIRMED のような専用ラベルに変更、または onAvailable の発火有無を別フィールドとして追加する。

課題 4：Android OSバージョン・端末依存の挙動差 深刻度：中

現状： 同一APに対しても端末・Android APIバージョンによってダイアログの表示パターンや Supplicant状態の発火タイミングが異なる可能性がある。

現在の実測は motorola edge 40 neo（Android API 35） 1機種のみで実施。

課題点： 結果の再現性・一般化可能性が未検証。複数機種・複数APIバージョンでの検証が必要。
