3.2 測定アプリケーション

本節では、測定アプリケーションの構成について述べる。 本アプリケーションは測定部、データ構成部、データ送信部の3つから構成される。 測定部は無線LAN環境の測定値を取得する。 データ構成部は、その測定値を送信用のデータに構成する。 データ送信部は、構成したデータをサーバへ送信する。 測定機能はそれぞれ独立した画面として実装されており、起動時のメインメニューから選択して起動する。[確認済: app/src/main/AndroidManifest.xml:30-57] 各画面および各部の具体的な実装は 5 章で述べる。

3.2.1 測定部

測定部はビーコン受信によるAP情報収集機能（APスキャン機能）、検出したAPへの接続試行によるサプリカント状態取得機能（パケット交換状態取得機能）、サーバからのファイルダウンロードによるスループット測定機能（スループット測定機能）の3つの機能から構成される。 3 つの機能は、それぞれ独立した画面として実装されている。[確認済: AndroidManifest.xml:44-56]

「APスキャン機能」は、物理層の指標であるRSSIと、ビーコンから取得できるAP情報を取得する。 測定の対象は測定端末が検出した全APである。 APスキャン機能で AP の電波から直接取得する指標を表 a-1 に示す。これら以外にも、サーバ送信時には導出指標やメタデータ（スキャン識別子、スキャン時刻、端末属性、位置情報など）が付与される。これらの定義は 5.1.2 で述べる。

3.2.3 データ送信部

データ送信部は、データ構成部が構成したデータをサーバへ送信する役割を担う。 送信にはHTTPを用い、送信タイミングは機能により異なる。ビーコンスキャン機能およびサプリカント状態取得機能は、「測定ごと」と「一定件数ごと（端末内に一度保留してからまとめて送信）」の 2 つのモードを備え、測定画面のスイッチで切り替える。[確認済: SimpleMeasurementActivity.kt:160-167, 415-417, 195-204、ConnectionMeasurementActivity.kt:193-200, 677-678] スループット測定機能は、測定ごとに 1 回送信する。[確認済: ThroughputActivity.kt:161-192] 送信に失敗した場合は、ビーコンスキャン機能およびサプリカント状態取得機能では、送信対象のデータを端末内に保持したまま、次回の送信機会に再送を試みる。[確認済: SimpleMeasurementActivity.kt:538-544、ConnectionMeasurementActivity.kt:1023-1029] スループット測定機能では失敗時に端末内へ保持せず、画面上に失敗を通知するのみとする。[確認済: ThroughputActivity.kt:359-369] また、送信先サーバの URL は 3 つの測定機能それぞれで独立に設定でき、測定画面上で変更できる。[確認済: ScanData.kt:14-28、SimpleMeasurementActivity.kt:169, 304-316、ConnectionMeasurementActivity.kt:251, 540-552、ThroughputActivity.kt:124-159] 送信したデータは、3.3節で述べるサーバ側で受信され、データベースに記録される。サーバ側の受信処理およびデータベースへの記録処理は本プロジェクトのソースコードには含まれないため、詳細は不明。

5章 機能

5.1 ビーコンスキャン機能

5.1.1 概要

ビーコンスキャン機能は、端末周辺の AP が発するビーコンから物理層・リンク層の情報を取得する機能である。[確認済: SimpleMeasurementActivity.kt:331-427、WifiUtils.kt:100-140] 取得する指標は 3.2.1 の表 a-1 に示したとおりで、BSSID、SSID、RSSI、周波数、帯域、チャネル幅、Wi-Fi 規格、セキュリティ分類、capabilities 生文字列、および各スキャンのメタデータ（スキャン ID、端末 ID、端末情報、スキャン時刻、ラベル、位置情報）を含む。[確認済: SimpleMeasurementActivity.kt:429-470] 測定の対象は、1 回のスキャンで端末が検出したすべての AP である。[確認済: SimpleMeasurementActivity.kt:377-382] 取得した測定値は、位置情報および時刻と対応付けられ、データ構成部が JSON オブジェクトへ変換して端末内の JSON ファイル（単独使用時は pending_simple_scans.json、サプリカント状態取得機能と併用する場合は pending_scans.json）へ追記し、データ送信部へ渡す。[確認済: SimpleMeasurementActivity.kt:410, 429-470、ScanData.kt:23-24, 69-80、ConnectionMeasurementActivity.kt:931-991]

5.1.2 取得・付与する指標の定義

5.1.1 で述べたとおり、ビーコンスキャン機能は AP の電波から物理層およびリンク層の情報を取得する（表 a-1）。しかし、直接取得した指標のみでは、研究目的に必要な以下の分析を行うことが難しい。そこで本機能は、直接取得した指標から導出した指標、および測定記録に付与するメタデータを合わせてサーバへ送信する。

  • 分析粒度: 中心周波数の数値そのままでは 2.4/5/6GHz の帯域別集計が困難である。また、準拠 IEEE 802.11 規格を表すコード値や、Android プラットフォームが整形した暗号・認証方式の記述文字列そのままでは、研究で扱う分類単位（規格世代、セキュリティ方式）に基づく集計が困難である。[推測: 研究データ用途を前提とした場合の必要性]
  • 測定記録の識別・紐付け: 複数のスキャン、複数の端末、複数の測定場所から得られた記録を区別・紐付けるため、記録単位で一意の識別子、測定時刻、セッション単位のラベルが必要である。[推測: サーバ側での記録管理を前提とした必要性]
  • 測定端末による差: 本研究は多数の一般利用者の端末を測定端末として想定しているため、端末ごとの機種差・Android プラットフォーム差により、取得できる指標の有無や取得値の挙動が異なる可能性がある。差を後から把握できるよう、端末属性を各スキャン記録に付与する。[確認済: CLAUDE.md「このアプリの役割（手段）」]
  • 屋外測定の前提: 本研究は屋外での利用を前提としているため、各スキャン記録に測定地点の位置情報を付与する。[確認済: CLAUDE.md「重要な設計方針」]

処理手順を実行順に示す。

  1. 測定者が画面上の「スキャン」ボタンを押下する。[確認済: SimpleMeasurementActivity.kt:189-193]
  2. ACCESS_FINE_LOCATION 権限を確認する。API 31 以上では NEARBY_WIFI_DEVICES 権限も確認する。未許可であれば ActivityResultContracts.RequestMultiplePermissions で要求する。[確認済: SimpleMeasurementActivity.kt:115-125, 318-329、AndroidManifest.xml:5-12]
  3. 自動スキャンがオフのときは、FusedLocationProviderClient.getCurrentLocation() に Priority.PRIORITY_HIGH_ACCURACY を指定して現在位置を取得する。[確認済: SimpleMeasurementActivity.kt:349-362]
  4. WifiManager.isWifiEnabled が false の場合は Toast を表示し、スキャンを中止する。[確認済: SimpleMeasurementActivity.kt:333-336]
  5. WifiManager.startScan() を呼び出し、スキャン要求を発行する。戻り値が false の場合（スロットリングされた場合）は Toast を表示し、スキャンを中止する。[確認済: SimpleMeasurementActivity.kt:344-347]
  6. SCAN_RESULTS_AVAILABLE_ACTION のブロードキャストを BroadcastReceiver で受信する。[確認済: SimpleMeasurementActivity.kt:109-113, 266]
  7. WifiManager.scanResults から ScanResult 一覧を取得する。[確認済: SimpleMeasurementActivity.kt:378]
  8. 各 AP について、以下の変換を行う。
    • band: ScanResult.frequency から導出（2400〜2500 MHz → 「2.4GHz」、4900〜5924 MHz → 「5GHz」、5925 MHz 以上 → 「6GHz」、それ以外 → 「Unknown」）。[確認済: WifiUtils.kt:9-14]
    • channel_width_mhz: ScanResult.channelWidth を 20 / 40 / 80 / 160 / 320 MHz に変換（CHANNEL_WIDTH_80MHZ_PLUS_MHZ は 160、整数値 5 は 320 として扱う）。[確認済: WifiUtils.kt:109-117]
    • wifi_standard: ScanResult.wifiStandard を規格ラベル文字列に変換。[確認済: WifiUtils.kt:16-24]
    • security: Build.VERSION.SDK_INT が TIRAMISU (API 33) 以上のときは ScanResult.securityTypes を集合として解析し、PSK と SAE の両方が含まれる場合は「WPA2/WPA3」、SAE/OWE/WPA3 EAP のいずれかが含まれる場合は「WPA3」、PSK のみの場合は capabilities の WPA2/RSN の有無で「WPA2」または「WPA」を区別、EAP または Passpoint がある場合は「WPA2」、WEP がある場合は「WEP」、それ以外は「Open」と判定する。API 33 未満では capabilities 文字列に対して同様の優先順位で判定する。[確認済: WifiUtils.kt:26-70]
    • mld_mac_address: Build.VERSION.SDK_INT が TIRAMISU 以上かつ ScanResult.apMldMacAddress が null でないときのみ値を設定し、それ以外は null とする。[確認済: WifiUtils.kt:118-120]
  9. スキャン 1 回分について UUID を生成し scan_id とする。各 AP の情報と、端末情報（Build.MANUFACTURER / Build.MODEL / Build.VERSION.SDK_INT）、永続保存した端末 UUID（device_id）、スキャン時刻（ロケール依存の yyyy-MM-dd'T'HH:mm:ss 形式）、ラベル、位置情報を 1 件の JSON オブジェクトにまとめる。[確認済: SimpleMeasurementActivity.kt:385, 429-468, 551-556]
  10. 構成した JSON オブジェクトを端末内の JSON 配列ファイル（pending_simple_scans.json）に追記する。[確認済: SimpleMeasurementActivity.kt:410, 469、ScanData.kt:76-80]
  11. 「測定直後に送信」モードが有効な場合、端末内ファイルに保留されたすべての JSON オブジェクトを 1 件ずつ POST 送信し、成功したものから削除する。送信中に失敗が発生した場合はその時点で送信を打ち切り、残りは次回の送信機会に試行する。[確認済: SimpleMeasurementActivity.kt:415-417, 508-549]
  12. 自動スキャンが有効な場合、スキャン開始時刻から 5000 ms 経過後に次のスキャンをスケジュールする。[確認済: ScanData.kt:29、SimpleMeasurementActivity.kt:395-398, 422-425]

使用する主な Android API: WifiManager.startScan()、WifiManager.scanResults、ScanResult、SUPPLICANT_STATE_CHANGED_ACTION、SCAN_RESULTS_AVAILABLE_ACTION、FusedLocationProviderClient、SharedPreferences、HttpURLConnection。[確認済: SimpleMeasurementActivity.kt 全体]

定数値: 自動スキャン間隔 5000 ms、HTTP 接続タイムアウト 5000 ms、HTTP 読み込みタイムアウト 10000 ms。[確認済: ScanData.kt:29、SimpleMeasurementActivity.kt:525-526]

スキップ・失敗条件:

  • WifiManager.isWifiEnabled が false: スキャンを実行せず中止する。[確認済: SimpleMeasurementActivity.kt:333-336]
  • 権限（ACCESS_FINE_LOCATION）が未許可: スキャンを実行せず権限要求を行う。[確認済: SimpleMeasurementActivity.kt:115-125, 318-329]
  • WifiManager.startScan() が false を返す（スロットリング）: Toast を表示してスキャンを中止する。[確認済: SimpleMeasurementActivity.kt:344-348]
  • スキャン結果が 0 件: 画面を「空」表示に更新してその回の処理を終了する。[確認済: SimpleMeasurementActivity.kt:389-400]
  • HTTP 応答コードが 200〜299 の範囲外、または例外発生、またはタイムアウト: 当該 JSON オブジェクトを端末内に保持したまま送信を打ち切る。[確認済: SimpleMeasurementActivity.kt:519-544]

5.2 サプリカント状態取得機能

5.2.1 概要

サプリカント状態取得機能は、スキャンで検出した AP に対して順次接続要求を発行し、SUPPLICANT_STATE_CHANGED_ACTION ブロードキャストで通知される SupplicantState の遷移を記録する機能である。[確認済: SupplicantMeasurer.kt:85-122, 140-159, 163-262] 取得する指標は 3.2.1 の表 a-2 に示した 3 項目（supplicant_states、supplicant_final_state、supplicant_elapsed_ms）に加え、5.2.2 で定義する接続要求 API 呼び出しログ（supplicant_api_calls）を含む計 4 項目である。[確認済: ScanData.kt:50-53、ConnectionMeasurementActivity.kt:948-965] 測定の対象は、スキャン後にユーザが選択した AP 群（手動測定時）、またはスキャンで検出した全 AP（自動スキャン時）である。[確認済: ConnectionMeasurementActivity.kt:282-307, 611-612, 843-852, 904-928] 取得した測定値は、ビーコンスキャン機能の結果と同一の AccessPoint オブジェクトに付加され、データ構成部が JSON へ変換して pending_scans.json に追記し、データ送信部へ渡す。[確認済: SupplicantMeasurer.kt:256-261、ConnectionMeasurementActivity.kt:675, 931-991]

5.2.2 取得する指標の定義

3.2.1 の表 a-2 では、本機能の主要出力である 3 指標（サプリカント状態遷移、最終状態、測定所要時間）を示した。これらに加えて、本機能はサプリカント状態遷移が一切観測されなかった場合に、その原因を切り分けられるよう、接続試行の起点となる API 呼び出し自体の実行結果も記録する。この追加指標の定義を以下に示す。

接続要求 API 呼び出しログ

本機能は、サプリカント状態遷移を観測するため、測定対象 AP への接続を Android に要求する API を呼び出す。接続要求 API 呼び出しログは、その API 呼び出しについて、呼び出し時の経過時間（測定開始からの ms）と呼び出し結果（例外が発生しなければ "OK"、発生した場合は例外クラス名とメッセージを連結した文字列）を記録したログである。[確認済: ScanData.kt:33-34、SupplicantMeasurer.kt:164-165, 172, 211-217] 1 件の AP 測定について、通常は 1 要素（API 呼び出しが 1 回実行される）、WEP セキュリティでスキップされた AP では 0 要素となる。[確認済: SupplicantMeasurer.kt:172, 174-177, 211-217] この記録により、API 呼び出し自体が例外で失敗したケース（状態遷移が一切観測されない）と、API 呼び出しは成功したが AP 側の応答がなくタイムアウトしたケースを区別できる。[推測: コード構造から]

5.2.3 機能詳細

処理手順を実行順に示す。

  1. Activity の生成時に、SUPPLICANT_STATE_CHANGED_ACTION を IntentFilter に指定した BroadcastReceiver を登録する。[確認済: SupplicantMeasurer.kt:124-131、ConnectionMeasurementActivity.kt:388]
  2. 測定対象の AP 一覧が確定すると、以下の 3〜13 を AP 1 件ごとに順番に繰り返す。[確認済: SupplicantMeasurer.kt:140-159]
  3. 測定開始時刻を記録し、状態遷移リスト、Continuation 参照、各種早期終了フラグを初期化する。[確認済: SupplicantMeasurer.kt:163-172]
  4. BSSID から android.net.MacAddress を構築し、WifiNetworkSpecifier.Builder に setBssid、必要に応じて setSsid を設定する。[確認済: SupplicantMeasurer.kt:275-279]
  5. セキュリティ分類に応じて WifiNetworkSpecifier.Builder に以下のいずれかを設定する。
    • security が「WEP」: null を返して本 AP をスキップ扱いとする（最終状態は SKIPPED）。[確認済: SupplicantMeasurer.kt:174-177, 281]
    • EAP 系（API 33 以上の WifiConfiguration.SECURITY_TYPE_EAP_WPA3_ENTERPRISE_192_BIT を含む場合）: setWpa3Enterprise192BitModeConfig() にダミー WifiEnterpriseConfig（PEAP + MSCHAPV2 + ユーザ "DUMMY_USER" + パスワード "DUMMY_MEAS_12345"）を設定する。[確認済: SupplicantMeasurer.kt:292, 301-314]
    • EAP 系（WPA3 Enterprise 標準モード）: setWpa3EnterpriseStandardModeConfig() に同ダミー構成を設定する。[確認済: SupplicantMeasurer.kt:293, 310-313]
    • その他の EAP: setWpa2EnterpriseConfig() に同ダミー構成を設定する。[確認済: SupplicantMeasurer.kt:315]
    • OWE: setIsEnhancedOpen(true) を設定する。[確認済: SupplicantMeasurer.kt:316]
    • security が「WPA3」または「WPA2/WPA3」: setWpa3Passphrase("DUMMY_MEAS_12345") を設定する。[確認済: SupplicantMeasurer.kt:317-318]
    • security が「WPA2」または「WPA」: setWpa2Passphrase("DUMMY_MEAS_12345") を設定する。[確認済: SupplicantMeasurer.kt:319-320]
    • security が「Open」: パスフレーズ指定なしで Builder.build() する。[確認済: SupplicantMeasurer.kt:308-322]
  6. NetworkRequest.Builder に TRANSPORT_WIFI と上記 WifiNetworkSpecifier を設定して NetworkRequest を構築する。[確認済: SupplicantMeasurer.kt:179-182]
  7. ConnectivityManager.NetworkCallback を生成し、onAvailable() で最終状態を "NETWORK_AVAILABLE" に設定して Continuation を再開するよう定義する。[確認済: SupplicantMeasurer.kt:187-195]
  8. kotlinx.coroutines.withTimeoutOrNull(10000L) 内で suspendCancellableCoroutine を開始し、Continuation への参照を保持する。[確認済: SupplicantMeasurer.kt:200-202]
  9. 無変化タイマーを 3000 ms で起動する。Continuation 参照をセットした後に ConnectivityManager.requestNetwork(request, callback, Handler) を呼び出す。例外が発生した場合は結果に例外クラス名とメッセージを記録し、最終状態を REQUEST_FAILED と判定するフラグを立てて Continuation を再開する。[確認済: SupplicantMeasurer.kt:209-222]
  10. BroadcastReceiver が SupplicantState を受信するたびに、状態名と測定開始からの経過ミリ秒を状態遷移リストに追加する。状態受信ごとに無変化タイマーを 3338 ms にリセットする。[確認済: SupplicantMeasurer.kt:86-99]
  11. 以下の条件のいずれかで Continuation を早期に再開する。
    • SupplicantState.COMPLETED を受信: 早期終了フラグを立てて再開する（最終状態は AUTH_COMPLETED）。[確認済: SupplicantMeasurer.kt:101-104, 238-245]
    • SupplicantState.ASSOCIATED を受信かつ ASSOCIATED 早期終了モードが有効: フラグを立てて再開する（最終状態は PRE_TIMEOUT_ASSOCIATED）。[確認済: SupplicantMeasurer.kt:105-110, 237]
    • SupplicantState.DISCONNECTED を受信かつ、それまでに ASSOCIATING / ASSOCIATED / FOUR_WAY_HANDSHAKE / GROUP_HANDSHAKE のいずれかを受信していた場合: フラグを立てて再開する（最終状態は PRE_TIMEOUT_<一つ前の状態>）。[確認済: SupplicantMeasurer.kt:111-118, 238-244]
    • NetworkCallback.onAvailable() が呼ばれた場合: 再開する（最終状態は NETWORK_AVAILABLE）。[確認済: SupplicantMeasurer.kt:188-194, 236]
    • 無変化タイマーが発火した場合: 再開する（最終状態は、遷移リストが空でなければ最も進んだ状態を用いて IDLE_<state>、空であれば IDLE_NULL）。[確認済: SupplicantMeasurer.kt:74-81, 246-249]
  12. 10000 ms（withTimeoutOrNull のタイムアウト）が経過しても早期終了条件が成立しなかった場合、最終状態は、遷移リストが空でなければ最も進んだ状態を用いて TIMEOUT_<state>、空であれば TIMEOUT_NULL とする。[確認済: SupplicantMeasurer.kt:200, 250-253]
  13. 無変化タイマーを停止し、ConnectivityManager.unregisterNetworkCallback() でコールバックを解除する。経過ミリ秒と遷移リスト、API 呼び出し記録、最終状態を測定結果として記録する。次の AP に進む前に 300 ms 待機する。[確認済: SupplicantMeasurer.kt:155, 225-262]
  14. 全 AP の測定が完了したら、各 AP の測定結果をデータ構成部へ渡す。[確認済: SupplicantMeasurer.kt:140-159、ConnectionMeasurementActivity.kt:669-675]

使用する主な Android API: ConnectivityManager.requestNetwork、ConnectivityManager.NetworkCallback、ConnectivityManager.unregisterNetworkCallback、WifiNetworkSpecifier.Builder、NetworkRequest.Builder、NetworkCapabilities.TRANSPORT_WIFI、WifiEnterpriseConfig、SupplicantState、SUPPLICANT_STATE_CHANGED_ACTION、BroadcastReceiver、MacAddress、Handler、kotlinx.coroutines.suspendCancellableCoroutine、kotlinx.coroutines.withTimeoutOrNull。[確認済: SupplicantMeasurer.kt 全体]

定数値: 試行開始から最初の状態を待つ無変化タイムアウト 3000 ms、状態受信後に次の状態を待つ無変化タイムアウト 3338 ms、全体タイムアウト 10000 ms、ダミーパスフレーズ "DUMMY_MEAS_12345"、AP 間の待機 300 ms。[確認済: SupplicantMeasurer.kt:27-30, 155]

スキップ・失敗条件:

  • security が「WEP」: 対象 AP の測定をスキップし、最終状態 SKIPPED で記録する。[確認済: SupplicantMeasurer.kt:281, 174-177]
  • BSSID から MacAddress が構築できない: 対象 AP の測定をスキップする（最終状態 SKIPPED）。[確認済: SupplicantMeasurer.kt:276, 174-177]
  • ConnectivityManager.requestNetwork() が例外をスローした: 最終状態 REQUEST_FAILED で記録する。[確認済: SupplicantMeasurer.kt:212-220, 235]
  • 状態遷移が 1 件も受信されず無変化タイマーが発火: 最終状態 IDLE_NULL。[確認済: SupplicantMeasurer.kt:246-249]
  • 10000 ms 経過しても早期終了条件も無変化タイマー発火も起きない: 最終状態は遷移リストに基づき TIMEOUT_<state> または TIMEOUT_NULL。[確認済: SupplicantMeasurer.kt:250-253]

5.3 スループット測定機能

5.3.1 概要

スループット測定機能は、端末が現在接続中の AP を経由して指定サーバからファイルを HTTP ダウンロードし、所要時間と転送バイト数からスループット（Mbps）を算出する機能である。[確認済: ThroughputActivity.kt:270-323] 取得する指標は 3.2.1 の表 a-3 に示した latitude、longitude、ssid、rssi、wifistandard、downloadfilesize、measure_time、throughput である。[確認済: ThroughputActivity.kt:49-58, 330-339] 測定の対象は、測定ボタン押下時点で端末が接続中の AP 1 台である。[確認済: ThroughputActivity.kt:237-268] 取得した測定値は Gson により JSON 文字列に変換され、データ送信部が選択された送信先サーバ URL へ HTTP POST で送信する。端末内への保留は行わない。[確認済: ThroughputActivity.kt:34, 330-340, 343-371]

5.3.2 機能詳細

処理手順を実行順に示す。

  1. Activity 生成時に ACCESS_FINE_LOCATION 権限を確認し、未許可の場合は要求する。[確認済: ThroughputActivity.kt:83-89, 107-110]
  2. 測定者がダウンロード元ファイル URL と送信先サーバ URL を Spinner から選択する。「自分で入力」を選んだ場合は EditText から URL を読み取る。[確認済: ThroughputActivity.kt:128-159]
  3. 測定者が「測定開始」ボタンを押下する。[確認済: ThroughputActivity.kt:161-192]
  4. FusedLocationProviderClient.getCurrentLocation() に Priority.PRIORITY_HIGH_ACCURACY を指定して緯度・経度を取得する。取得に失敗した場合は Toast を表示して測定を中断する。[確認済: ThroughputActivity.kt:203-234]
  5. WifiManager.connectionInfo から接続中 AP の SSID、RSSI、wifiStandard を取得する。SSID が null または文字列 "<unknown ssid>" の場合は測定を中断する。[確認済: ThroughputActivity.kt:237-268]
  6. API 30 以上では WifiInfo.wifiStandard の値から規格ラベル（"802.11be" / "802.11ax" / "802.11ac" / "802.11n" / 2.4GHz 帯なら "802.11b/g" それ以外なら "802.11a" / "Unknown"）に変換する。API 30 未満では WifiInfo.frequency から 2.4GHz 帯なら "2.4GHz帯 (b/g/n)"、5GHz 帯なら "5GHz帯 (a/n/ac)"、その他は "Unknown" とする。[確認済: ThroughputActivity.kt:243-259]
  7. 測定開始時刻を System.currentTimeMillis() で記録する。[確認済: ThroughputActivity.kt:272]
  8. kotlinx.coroutines.withTimeoutOrNull(5000L) 内で以下を実行する。
    • java.net.URL(downloadFileUrl).openConnection() as java.net.HttpURLConnection で接続を開く。
    • useCaches = false、Cache-Control: no-cache、Pragma: no-cache をリクエストヘッダに設定する。
    • 8192 バイト（8 × 1024）のバッファで InputStream.read() を戻り値が -1 になるまで繰り返し、総バイト数を加算する。
    • InputStream と HttpURLConnection を閉じる。
    [確認済: ThroughputActivity.kt:281-294]
  9. 5000 ms でタイムアウトした場合はタイムアウトフラグを立てる。例外が発生した場合は Toast を表示して測定を中断する。[確認済: ThroughputActivity.kt:294, 316-322]
  10. 終了時刻と経過時間（秒）、スループット（Mbps = 総バイト数 × 8 ÷ (経過秒 × 1,000,000)、経過秒が 0 の場合は 0.0）、ダウンロードファイルサイズ（総バイト数 ÷ 1,000,000、MB 単位の整数）を算出する。[確認済: ThroughputActivity.kt:296-299]
  11. 緯度、経度、SSID（前後の引用符を除去）、RSSI、規格ラベル、ファイルサイズ、所要時間、スループットを FlatCollectedData 風の単一オブジェクトにまとめ、Gson.toJson() で JSON 文字列に変換する。[確認済: ThroughputActivity.kt:49-58, 325-341]
  12. kotlinx.coroutines.withTimeoutOrNull(5000L) 内で以下を実行する。
    • java.net.URL(destinationServerUrl).openConnection() as java.net.HttpURLConnection。
    • requestMethod = "POST"、Content-Type: application/json、doOutput = true。
    • OutputStreamWriter に UTF-8 で JSON を書き出す。
    • responseCode を取得し、200 でなければ例外として扱う。
    [確認済: ThroughputActivity.kt:343-357]
  13. 送信が成功した場合は測定回数カウンタをインクリメントし、画面に表示する。失敗した場合は Toast を表示する（端末内への保留は行わない）。[確認済: ThroughputActivity.kt:170-177, 359-369]

使用する主な Android API: WifiManager.connectionInfo、WifiInfo.wifiStandard、WifiInfo.rssi、WifiInfo.ssid、WifiInfo.frequency、ScanResult（規格定数 WIFI_STANDARD_11BE 等）、FusedLocationProviderClient.getCurrentLocation、Priority.PRIORITY_HIGH_ACCURACY、java.net.URL、java.net.HttpURLConnection、kotlinx.coroutines.withTimeoutOrNull、com.google.gson.Gson。[確認済: ThroughputActivity.kt 全体]

定数値: ダウンロードタイムアウト 5000 ms、送信タイムアウト 5000 ms、ダウンロード読み込みバッファサイズ 8192 バイト（8 × 1024）、スループット算出分母 1,000,000、ファイルサイズ算出分母 1,000,000。[確認済: ThroughputActivity.kt:281, 286, 298-299, 344]

スキップ・失敗条件:

  • ACCESS_FINE_LOCATION 権限未許可: Toast を表示し測定を中断する。[確認済: ThroughputActivity.kt:204-210]
  • 位置情報取得失敗（null 返却または例外）: Toast を表示し測定を中断する。[確認済: ThroughputActivity.kt:216-233]

付録 B: 草稿とコードの相違

  1. サプリカント測定の対象
    草稿 3.2.1: 「パケット交換状態取得機能」の「測定の対象は検出した全APである」。
    コード: 手動測定経路では、スキャン結果から測定者が選択した AP のみが測定対象となる。全 AP が測定対象になるのは自動スキャン経路のみ。[確認済: ConnectionMeasurementActivity.kt:282-307, 611-612, 843-852, 904-928]
    本文での対応: 5.1 概要および 3.2.1 本文で「手動測定時はユーザが選択した AP、自動スキャン時は検出した全 AP」と記述した。
  2. 送信経路の分離
    草稿 3.2.3: 「データ送信部は、データ構成部が構成したデータをサーバへ送信する」（送信経路が 1 つであるかのような記述）。
    コード: ビーコンスキャン機能／サプリカント状態取得機能の送信経路と、スループット測定機能の送信経路は別実装・別 URL・別 JSON 構造であり、送信先サーバ URL も独立に設定される。[確認済: ScanData.kt:14-28、SimpleMeasurementActivity.kt:508-549、ConnectionMeasurementActivity.kt:993-1034、ThroughputActivity.kt:343-371]
    本文での対応: 3.2.3 本文で「送信先の URL はビーコンスキャン機能、サプリカント状態取得機能、スループット測定機能でそれぞれ独立に設定可能」と記述した。
  3. 送信タイミングと失敗時の扱い
    草稿 3.2.3: 「【測定ごと／一定件数ごと】に送信する。送信に失敗した場合は、【再送する／端末内に保持する】」。
    コード: ビーコンスキャン／サプリカントは UI スイッチにより「測定直後の送信」と「保留」の 2 モードを切替、失敗時は端末内 JSON ファイルを保持し次の送信機会に再送試行する。スループットは測定ごとに 1 回送信し、失敗時は保留せず Toast 表示のみ。[確認済: SimpleMeasurementActivity.kt:160-167, 415-417, 508-549、ConnectionMeasurementActivity.kt:193-200, 677-678, 993-1034、ThroughputActivity.kt:161-192, 343-371]
    本文での対応: 3.2.3 本文でこの実装通りに記述した。
  4. 測定値に対応付ける「時刻」
    草稿 3.2.1: 「測定部は、取得した測定値に位置情報と時刻を対応付け、データ構成部へ渡す」。
    コード: ビーコン／サプリカントの送信 JSON には scanned_at（ISO 8601 風の時刻文字列）が含まれるが、スループット測定の送信 JSON には時刻フィールドが含まれず、ダウンロード所要時間 measure_time のみが含まれる。[確認済: SimpleMeasurementActivity.kt:430, 456、ConnectionMeasurementActivity.kt:932, 977、ThroughputActivity.kt:49-58, 325-341]
    本文での対応: 3.2.1 末尾に「スループット測定機能は時刻を測定値として JSON に格納しない」と補足した。
