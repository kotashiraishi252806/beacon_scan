FACT — 事 実
先行研究アプリのコードから確認できた事実
サプリカント取得の方法と測定範囲
測定できるAPは接続中の1台のみであり、その接続先APの状態を読み取っている。

使用API：wifiManager.connectionInfo.supplicantState

このAPIは現在接続中のAP1台の情報を返す。 OSから接続状態の変化が通知されたタイミング（NETWORK_STATE_CHANGED_ACTION）で読み取っている。
wifiManager.connectionInfo.supplicantState // 接続中の1台のAPの状態のみ返す // NETWORK_STATE_CHANGED_ACTION（OS からの通知）受信時に呼び出す // → 前回から変化していたときのみ CSV に書き込む
サーバへのデータ送信とDBスキーマ
サーバへの送信機能が確認できた。MySQL DB（new_index_wifi）へHTTP POSTで送信し、2つのテーブルに格納する。

beacon_data（POST先: /api/upload/beacon）：Wi-Fiスキャンデータ（SSID・BSSID・RSSI・周波数・Wi-Fi規格・位置情報など）
state_data（POST先: /api/upload/state）：Wi-Fi接続状態データ（supplicantState・detailedState・リンク速度・IPアドレスなど）

格納するカラム構成から、state_dataは接続中の1台の状態遷移を時系列で記録する設計であることが読み取れる。
CONSIDERATION — 考 察
事実から考えられること
測定範囲について（事実①より）
公衆無線LANのように同一SSIDが複数のAPに設定されている環境では、 接続中の1台しか測定できない。

同一SSIDが設定されているAPを網羅的に測定できたほうが、 その無線LAN環境をより有意義に把握できるのではないか。
対応する事実：測定できるAPは接続中の1台のみ
データ管理について（事実②より）
先行研究にもDB保存・サーバ送信の仕組みはあった。しかし beacon_data に格納されるのも、 アプリ側で取得できた接続中の1台分のデータのみであり、測定範囲の制約は変わらない。

state_data はカラム構成（supplicantState・detailedState・リンク速度・IPアドレスなど）から、接続中APの状態を時系列で記録することを目的とした設計であると読み取れる。

本質的な課題は「サーバ送信の有無」ではなく、全APを測定するアプリ側の手段の欠如にある。
対応する事実：アプリ側の測定対象は接続中の1台のみ（事実①）
PROPOSAL — 提 案
推測をもとにした本研究のアプローチ
全AP測定のための能動的接続試行
同一SSIDが設定されている各APを個別に測定するには、 BSSIDを指定してアプリ側から能動的に接続試行を行う 必要がある。
本研究では WifiNetworkSpecifier + requestNetwork() を用いて、 スキャンで検出した全APに対して順番に接続試行を行う。
対応する推測：OSのAP選択挙動、測定対象の制御不可
全AP測定に対応したDBスキーマの再設計・送信実装（考察②より）
先行研究のDBスキーマは接続中の1台分のデータを前提としており、 スキャンで検出した全APの測定結果を格納する構造になっていない。

本研究では、1回のスキャンで検出した全APの情報（BSSID・RSSI・セキュリティ・Wi-Fi規格・ サプリカント試行結果など）を1エントリとして格納できるスキーマを新たに定義した。

端末はスキャン結果をJSON形式でサーバへHTTP POSTし、サーバはスキーマに従いDBへ格納する。 送信失敗時は端末内に保持し、次回以降に再送する。
対応する考察：全APを網羅的に測定・保存する構造が必要　／　先行研究のスキーマは接続中1台分が前提
