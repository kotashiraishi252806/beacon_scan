接続試行の定義に関する議論まとめ（2026-09-25）

このドキュメントは、測定Androidアプリにおける「接続試行」の定義を確立するために行った議論の記録です。 サーバサイドの分析Webアプリ開発への引き継ぎ資料として作成しています。

1. 議論の目的

  • 論文において接続試行の詳細を正確に記述すること
  • データ集計時の分類基準（接続試行件数など）を明確にすること
  • ゴール：接続試行を定義し、接続試行回数をカウントできるようにすること

2. アプリの現状確認

2-1. アプリの接続試行処理の概要

アプリはWiFiスキャンで検出した各APに対して順次 measureForAp() を呼び出す（SupplicantMeasurer.kt）。

measureAll() → AP1件ごとに measureForAp() を呼び出す
  → connectivityManager.requestNetwork() を1回呼び出す
  → SUPPLICANT_STATE_CHANGED_ACTION を受信し、遷移状態を supplicantTransitions に記録
  → supplicantFinalState に結果を格納して返す

2-2. 現状の課題

  • 接続試行回数を格納する変数が存在しない
  • 「接続試行」の定義がコード上で明示されていない
  • SKIPPED・CANCELLED は requestNetwork() を呼ばないが、結果リスト上は他の試行結果と同列に並ぶ

3. 接続試行の定義の検討

3-1. 候補① requestNetwork() 呼び出し

ConnectivityManager.requestNetwork() はOSへの接続要求の発行であり、端末からAPへの接続が始まったわけではない。厳密には「接続試行」の開始点として不適切。

3-2. IEEE 802.11 接続シーケンス

順序フェーズ内容
1スキャンProbe Request/Response によるAP探索（Active）またはビーコン受信（Passive）
2認証（Authentication）Authentication Request/Response の交換
3関連付け（Association）Association Request/Response の交換
4鍵交換（Key Exchange）WPA2/WPA3 の場合、4-Way Handshake
5接続完了データ通信が可能な状態

3-3. Active/Passive スキャンと接続試行の関係

  • Active スキャン：Probe Request を全AP宛に送信してAP探索を行う
  • Passive スキャン：ビーコンを受信してAP探索を行う
  • Probe Request は探索目的で不特定多数のAP宛に送るため、特定APへの接続意図を持たない → 接続試行ではない
  • このアプリは WifiManager.startScan() を使用するが、Active/Passive のどちらが使われるかはOS・ドライバ・電波法規制ドメインによって決定され、アプリからは制御も観測も不可能

3-4. 採択した定義

接続試行1回の定義：特定のAPに対してAuthentication Requestフレームを送信した1回

採択理由：
  • Authentication Request は特定のAPを宛先として送信する最初のフレームであり、接続意図が明確
  • Active/Passive 問わず、特定APへの接続シーケンスは必ずAuthenticationフェーズから始まる（IEEE 802.11規格上）
  • Probe Request と異なり、不特定多数宛ではなく特定AP宛である

4. 実装方針

4-1. Authentication Request フレームの直接カウントは不可能

Authentication Request フレームはレイヤー2（802.11 MACフレーム）であり、通常のAndroidアプリからは直接観測できない。パケットキャプチャにはroot権限または特殊な権限が必要。

4-2. 近似手段：SupplicantState.AUTHENTICATING 遷移のカウント

アプリは SUPPLICANT_STATE_CHANGED_ACTION をすでに受信しており、supplicantTransitions に全状態遷移を記録済み（SupplicantMeasurer.kt:68）。

supplicantTransitions.add(state.name)

supplicantTransitions 中の "AUTHENTICATING" の出現回数が、接続試行回数の近似値となる。

注意： SupplicantState.AUTHENTICATING は wpa_supplicant の内部状態であり、Authentication Request フレームの送信と1対1で対応することは Android API ドキュメント上で保証されていない。論文上は「近似値」として明示する必要がある。

4-3. カウントの実施場所：サーバサイド

アプリへの余計な計算リソース消費を避けるため、カウントはサーバサイドで行う方針とした。

アプリはすでに supplicant_states（全遷移リスト）をAP単位でサーバに送信している。サーバサイドでそのリスト中の "AUTHENTICATING" の出現回数を数えることで実現可能。アプリ側の変更は不要。

5. サーバサイドへの要件

5-1. 既存JSONスキーマの該当フィールド

{
  "access_points": [
    {
      "supplicant_states": ["SCANNING", "AUTHENTICATING", "ASSOCIATING", ...],  ← このフィールドを使用
      "supplicant_final_state": "COMPLETED" | "FAILED_AT_*" | "TIMEOUT_AT_*" | ...
    }
  ]
}

5-2. 集計方法

集計単位算出方法格納場所の提案
AP単位の接続試行回数各APの supplicant_states 中の "AUTHENTICATING" の出現回数AP単位レコード（下位層）
スキャンセッション単位の合計接続試行回数スキャン内全APの上記値の総和スキャンエントリのメタ情報（上位層）

5-3. supplicant_final_state の値一覧（参考）

値意味
COMPLETED接続成功
FAILED_AT_<STATE>該当状態で失敗（例：FAILED_AT_DISCONNECTED）
TIMEOUT_AT_<STATE>該当状態でタイムアウト（最大10秒）
NOT_FOUNDAPが見つからなかった（onUnavailable かつ遷移なし）
SKIPPEDWEP APのためスキップ（接続試行なし）
CANCELLED停止ボタンによるキャンセル（接続試行なし）
